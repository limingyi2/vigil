# 排错清单

报错先定位，再改。**没看到真实报错原文之前不要给修复方案。**

## 1. 先要证据

- 完整报错（不是"报错了"这三个字），包括 traceback 最里层那一帧
- 触发路径：哪一步操作、什么输入、能否稳定复现
- 环境：操作系统、运行时版本、依赖版本、最近一次"之前还好好的"是什么时候

## 2. 分三类，别混在一起查

| 类别 | 特征 | 先查什么 |
| --- | --- | --- |
| 环境/依赖 | 换机器就好了、装上某个包之后开始 | 版本、路径、权限、编码 |
| 逻辑 | 稳定复现，输入决定结果 | 边界值、空值、类型、并发 |
| 集成 | 时好时坏，日志对不上 | 时序、超时、重试、幂等 |

## 3. 一次只改一处

- 每次只改一个假设点，改完立刻验证
- 同时改三处然后"好了"，等于没修 —— 下次复现时不知道是哪一处起作用
- 改不动就先加日志/断言把状态钉出来，别靠猜

## 4. 修复的最低标准

- 能说清"为什么原来是错的"（不是"这样就好了"）
- 给出最小可验证的改动，不顺手重构无关代码
- 补一条能复现原问题的验证方式（测试、命令、或明确的操作步骤）
- 说明这个改动会不会影响别的路径

## 5. 明确不做什么

- 不编造不存在的 API、参数、包名 —— 不确定就说不确定
- 不用 `try: ... except: pass` 把错误藏起来
- 不为了"让它跑起来"而放宽校验或跳过鉴权
- 不假设用户的目录结构、字段名、接口返回格式，先问或先读

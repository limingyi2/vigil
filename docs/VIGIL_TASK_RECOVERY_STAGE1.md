## 一、第一步：当前执行链梳理

### 1.1 三条执行路径（按现有代码追踪）

**关键事实（修订 1 的前提）**：当前存在**三条**互不相同的入口路径，且**首期想要的可恢复任务，目前没有任何一条能稳定进入**。

| 路径 | 入口 | 是否经过规划 | 说明 |
|---|---|---|---|
| **A 普通聊天接口** | `POST /api/chat`（`server.py:1918`） | 有条件：启发式命中才走 Planner | 见 §1.6 的 D2 旁路，部分本地路径请求会**绕过 Planner 直走 FC** |
| **B 流式聊天接口** | `POST /api/chat/stream`（`server.py:2202`） | **否**：`schema_needed()` 为真时直接 `brain.chat()`，否则 SSE 流式直答 | **桌面纯文本默认走这条**；该路径直接调用 Brain，**不经过 planner** |
| **C 其他** | `run_hybrid_delegation_direct` 前置委派（`server.py:469`） | 否 | 规划前确定性截获本地勘察任务，单次收尾 |

#### 路径 A：Planner 路径（Plan-and-Execute）

```
用户请求
  └─ ① run_hybrid_delegation_direct(text, src)   规划前确定性委派（server.py:469）
       │ 命中 → 直接执行委派 + 单次收尾 → return
       └─ 未命中 → planner.plan_decision(text)   启发式判断（server.py:499，不打模型）
            └─ 命中 → planner.plan(text, src)    便宜 flash 模型列步骤（超时30s，≤5步）
                 └─ planner.execute_plan(steps, src, allowed_tools)  逐步执行（fail-closed 授权交集）
                      └─ _once(build_final_prompt(...), no_tools=True)  主模型组织回答
                           └─ planner.verify_result(text, results, ans)  轻量结果检查器
                                └─ 有问题 → _once(build_revise_prompt(...))  最多修一次
```

#### 路径 B：普通工具循环（原生 FC / ReAct）

```
brain.chat → brain.draft_native(user_text, ...)（brain.py:927）
  └─ for _round in range(_max_rounds=24):
        ├─ 预算检查：time.time()-_t0 > _budget_s(270s) → break
        ├─ mp.chat(payload, timeout=90)                 每轮 90s
        ├─ 有 tool_calls → _tools.invoke_spec(...) 执行 → role:"tool" 回灌 → 下一轮
        └─ 无 tool_calls → 最终回复
  └─ 轮次/预算用尽 → 补一次 no-tools 收尾（timeout=60）
```

### 1.2 授权 / 执行 / 返回责任划分

- **谁检查权限**：`planner.execute_plan`（`planner.py:399`）取 `tools.all_specs(brain, src)` 与本轮 allow-list 的交集；**无 allow-list 时 fail closed**。server 在 `server.py:557` 现算 allow-list。FC 路径靠工具表本身过滤 + `localtools.call` 的 `clearance(risk)` 二次拦截（`localtools.py:453`）。
- **谁真正执行**：内置/插件 `tools.run_tool`（`tools.py:444`）；动态技能 `skill.invoke_tool`；本机操控 `localtools.call`（**阻塞等待**客户端轮询认领并回结果，`localtools.py:433`）；混合委派 `delegation.bridge`。
- **谁返回结果**：`localtools.resolve`（客户端轮询交回，`localtools.py:551`）；其余为函数返回值。FC 路径把返回文本作为 `role:"tool"` 回灌。

### 1.3 七个必答问题

| 检查内容 | 现状结论 | 依据 |
|---|---|---|
| **请求入口** | 三条路径并存（§1.1）；**当前没有持久化的"任务"实体**，一次请求 = 一次会话调用 | `server.py:208/209/1918/2202` |
| **计划产生** | 步骤明确（≤5 步）；**执行中不能改计划**：`execute_plan` 顺序跑完；`verify_result` 只修正"回答"，不改步骤 | `planner.py:391`、`server.py:569-583` |
| **工具调用** | 权限由 `execute_plan` 授权交集判（fail closed）；执行 `tools.run_tool`；本机结果由 `localtools.resolve` 返回 | `planner.py:399`、`tools.py:444`、`localtools.py:551` |
| **超时与错误** | **超时后工具可能仍在执行**：`localtools.call` 超时返回"……别当它做完了"（`localtools.py:503-512`）。FC 每轮 90s、总 270s；Planner flash 30s/20s | `localtools.py:503`、`brain.py:1053-1054` |
| **结果保存** | 执行结果**只活在本次调用栈**（`results` 局部变量）+ 内存 `brain.hist`；**无步骤级检查点** | `server.py:563-570`、`brain.py:1561` |
| **页面关系** | 页面关闭**不影响**服务端任务；本机操控靠客户端**后台轮询**（`localtools.take`）。页面关了但客户端进程在轮询就仍可能执行 | `localtools.py:530` |
| **并发关系** | **同一会话不能同时启动两个任务**：`_chat_lock()`（`server.py:292`），上限 `CHAT_LOCK_WAIT=300`；抢不到抛 `_Busy` → 返回"忙碌"（`server.py:820`）。**注意：该锁只包住 `_once()` 单次调用（`server.py:434`），两次 `_once` 之间会释放**，不保护整个 Planner 执行过程 | `server.py:158/292/434/820` |

### 1.6 【修订 1】首期可达的原生任务入口

**问题**：文档只覆盖 Planner，但桌面纯文本默认走 `/api/chat/stream`（直接调 Brain，不规划）；`/api/chat` 的 D2 分支还会把带绝对本地路径的请求**绕过 Planner 直走 FC**（`server.py:522-543`）。因此"用户怎样创建一个可恢复任务、该入口怎样稳定进入新任务执行链"必须显式定义。

**修订：新增独立的任务入口，与聊天入口解耦。**

1. **新入口 `POST /api/task/start`**（本契约定义入口契约；**实际接线在后续阶段**，阶段二不落该 HTTP 接口）：
   - 请求体：`{ "goal": str, "src": str, "workspace_dir": str, "budget": {...} }`。
   - **不经过 `plan_decision` 启发式**：任务即显式意图，**必须**走"规划→执行"链（或直接接受调用方给定的显式步骤）。
   - **不经过 D2 旁路、不经过 `run_hybrid_delegation_direct`**：这两者都是"聊天请求的隐式路由"，任务入口不使用它们。这意味着任务入口可在**无绝对路径**的场景下也稳定进入规划链路。
   - **不接受 `/api/chat/stream`**：任务的**后台执行独立于连接**；展示层允许订阅**可重连的事件流**（见 §七），不使用聊天 SSE 作为任务传输。
   - 桌面端入口：聊天中的"新建任务"入口调用该接口；返回 `task_id` 与任务卡数据。

2. **任务级锁（新）**：任务执行器持有**任务级执行锁** `TASK_LOCK`，覆盖整个任务生命周期，而**不是**现有的 `_chat_lock`。原因：`_chat_lock` 只包住单次 `_once()`（`server.py:434`），`execute_plan` 与多次 `_once` 之间锁已释放，无法阻止"任务正在跑时又启动一份"。

3. **不改变聊天行为**：`/api/chat`、`/api/chat/stream` 的现有分支（含 D2 旁路、前置委派）**保持原样**；普通聊天仍不是任务，不落检查点。

4. **设备鉴权**：把 `/api/task/` 前缀加入桌宠（`admin` 角色）可用接口，受限设备（`device`）默认不放行（`DEVICE_POST_ALLOW`，`server.py:207`）。

> 结论：**"聊天"与"任务"从此是两个入口**。只有 `/api/task/start` 创建的才是可恢复任务；聊天中的自由工具循环不纳入续跑。

## 二、第二步：贯穿开发与验收的样例任务

### 2.1 样例任务与四个步骤

> **查找指定目录中的日志，读取相关错误，生成问题汇总，并保存报告。**

| 步骤 | 类型 | 输入 | 完成条件 |
|---|---|---|---|
| **S1 查找日志** | 工具步骤 | 授权目录、查找条件 | 得到有效的文件清单 |
| **S2 读取并分析** | 工具步骤 | 文件清单、读取范围 | 保存分析所需的结果和来源 |
| **S3 生成汇总** | 模型步骤 | 已取得的材料 | 形成有依据的报告内容 |
| **S4 保存报告** | 工具步骤（写） | 报告内容、目标路径 | 文件存在，内容校验通过 |

### 2.2 【修订 2】步骤类型及输入、输出传递规则

**问题**：现有 `execute_plan` 遇到 `tool=None` 只 `results.append((step_desc, tool, arg, None))`（`planner.py:404-406`），**不会执行"生成汇总"**；`verify_result` 检查的是**整份最终回答**（`planner.py:479`），**不会逐步验证**。因此样例的四步无法直接映射现有执行器。

**修订：定义三类步骤，并规定执行与验证方式。**

| 类型 | `tool` 字段 | 由谁执行 | 产物 | 验证方式 |
|---|---|---|---|---|
| **工具步骤 tool** | 工具名 + **经工具 schema 校验的 `args` 对象** | 执行器调用 `run_tool`/`invoke_spec` | 工具返回文本 → 存 `result_ref` | 该步骤类型的完成证据（§5.1） |
| **模型步骤 model** | `None` | **执行器必须真正执行**：把上游 `result_ref` 内容拼进提示，调用模型产出结果 | 模型产出写入 `result_ref` | 产出非空且可被下游引用 |
| **收尾步骤 finalize** | `None`（`no_tools=True`） | 由 `_once(..., no_tools=True)` 执行 | **用户可见回答**（非中间结果） | `verify_result` 检查回答是否用上结果、是否编造 |

**输入/输出传递规则**：

- 每个步骤的产物统一存进**任务命名空间**：`result://<task_id>/<step_id>/<name>`。
- 下游步骤通过 `args` 中的**显式引用**（`{"$ref": "result://..."}`）引用上游产物。
- 执行器在步骤启动前**解析引用**，把上游产物**按字段注入该步骤的 `args`**。
- **工具参数一律为 `args` 对象**，必须经对应工具的 **schema 校验**后才能执行（`path`、`pattern`、写入内容等都作为具名键）。示例：S1 `args={"dir":"D:\vigil\logs","pattern":"*.log"}`；S4 `args={"path":"D:\vigil\logs\summary_report.md","content":<引用解析结果>}`。
- **`result://` 引用解析后注入哪个字段，由步骤输入显式声明**：如 S4 的 `input={"args":{"path":...,"content":{"$ref":"result://<task_id>/step_s3/report.md"}}}`，执行器把 `$ref` 解析为 S3 产物内容后写入 `args.content`。
- **兼容**：旧 Planner 的单字符串 `arg` 在解析阶段转换为 `{"arg": s}`，**仅作兼容**；新任务一律使用 `args` 对象。
- **S3 → S4 的传递**：S3 是模型步骤，产物落 `result://.../step_s3/report.md`（含 `result_digest`）；S4 的 `args={"path":...,"content":{"$ref":"result://.../step_s3/report.md"}}`，执行器解析 `$ref` 后写入 `args.content`，完成条件为"文件存在且内容校验通过"。
- **首期实现顺序**：先验证 S1–S3（只读 + 模型），再接入 S4（写操作，走"待核对"链路）。

> 现有 `execute_plan` 的对外签名与"tool=None 记 None"的行为**仅在本契约中重新定义**；执行器分派、工具派发协议与入口接线在**后续阶段**实现，**阶段二只落存储与状态事务**（见 §10）。本文档不改 FC 路径。

## 三、第三步：任务 / 步骤 / 执行尝试 三对象定义

### 3.1 三个对象

| 对象 | 含义 | 关键字段 |
|---|---|---|
| **任务 Task** | 用户希望完成的整体目标 | 任务 ID、目标、归属、工作目录、计划版本、状态、预算 |
| **步骤 Step** | 可以单独执行和验证的一段工作 | 步骤 ID、类型、依赖、输入、完成条件、结果引用、风险类型 |
| **执行尝试 Attempt** | 某一步实际执行的一次过程 | 尝试 ID、执行序号、启动时间、工具请求身份、结果、错误、验证记录 |

差异化示例："保存报告"始终是**同一个步骤（Step）**，但第一次超时、核对后再次执行，应留下**两条尝试（Attempt）**记录。

### 3.2 首期规则

1. **计划版本**：开始执行后计划版本固定；修改步骤含义、重要输入或目标时**生成新版本**（不原地改写旧版本，旧版本历史保留）。
2. **结果引用**：工具输出较大时保存 `result_ref`；检查点只记**摘要 + 校验信息**。
3. **归属绑定**：任务绑定用户、渠道、人格及授权工作目录；**恢复时重新检查当前权限**。
4. **凭据边界**：恢复所需内容保存在本机任务库；**凭据与完整思考链不进入检查点**。
5. **历史不可覆盖**：取消、失败、完成等历史记录**只追加不覆盖**。

### 3.4 【修订 6】输入指纹、结果摘要与依赖失效

**问题**：第一稿场景 5 把"当前源文件摘要"与 `result_digest` 比较，但 `result_digest` 代表**工具输出**（可能是截取内容或分析文本），二者不是同一层数据，比较无意义。

**修订：两个哈希严格分层。**

| 名称 | 定义 | 用途 | 计算对象 |
|---|---|---|---|
| **input_fingerprint**（输入指纹） | 对某步骤**声明的输入**取哈希 | 检测**输入是否变化** | 上游产物摘要 / 源文件的 `内容哈希 + mtime` |
| **result_digest**（结果摘要） | 对该步骤**自身产出**取哈希 | 校验**结果是否仍有效** | 步骤写出的文件 / 存储的产出内容 |

**依赖失效规则**：

1. 每个步骤在启动时计算并记录 `input_fingerprint`。
2. 恢复或继续时**重算当前输入指纹**：
   - 与记录一致 → 结果仍有效，可跳过（工作去重）。
   - 不一致 → 该步骤结果**失效**：置为"待核对/待执行"，并**向下游传播**——所有 `depends_on` 该步骤的下游结果标记为**受影响**（不再视为有效，需重新验证或重算）。
3. **失效时生成新计划版本 `plan_version+1`**（§3.2 规则 1），使旧版本历史与新旧结果并存，不覆盖。
4. **永不**拿源文件哈希去比 `result_digest`；两个哈希只在各自层级内比较。

**场景 5 的正确做法（替换第一稿）**：S2 记录 `input_fingerprint`（其读取源文件的 `内容哈希+mtime`）。恢复时重算源文件指纹：不一致 → S2 结果失效 → S3/S4 标记受影响 → 生成 `plan_version+1` 重新分析；旧 `plan_version=1` 的历史保留。

### 4.1 步骤（Step）状态

| 状态 | 含义 |

| `待执行` pending | 尚未启动 |
| `执行中` running | 已开始一次执行尝试 |
| `等待用户` waiting_user | 需要审批或补充输入，并记录具体原因 |
| `验证中` verifying | 已收到**明确结果**，正在检查完成条件 |

### 4.3 两个必须避免的错误

1. **工具请求超时 ≠ "没有执行"**：超时只能进入 `待核对`（T5），**不得**记成失败或"未执行"。
2. **模型说"完成了" ≠ "步骤完成"**：`verify_result` 只是**辅助检查**，不能作为 T3 的唯一证据；T3 必须依赖**外部可验证的完成证据**。

### 4.4 任务总体状态汇总规则

优先级（高 → 低）：

```
已取消 > 待核对 > 等待用户 > 已中断 > 失败 > 执行中 > 验证中 > 待执行 > 已完成
```

- **只要有任一步骤 `待核对`，整个任务不得显示"完成"**（硬规则）。
- 有 `已取消` 步骤 → 任务 `已取消`（终态，不可翻回）。
- 全部 `已完成` → 任务 `已完成`。
- 存在 `已中断` 且无更高级状态 → 任务 `已中断`。

### 4.6 【修订 3 附】T2 与 T5 的冲突消解规则

## 五、第五步：完成证据与去重规则

### 5.1 完成证据矩阵

| 步骤类型 | 可采用的证据 |
|---|---|
| 文件查找 | 查询范围、条件和**有效清单** |
| 文件读取 | 来源、读取范围、内容或结果引用（`result_ref` + `result_digest`） |
| 分析整理（模型步骤） | 输入来源、产出内容、**规定的检查结果** |
| 文件保存 | **实际路径、文件存在性、内容校验** |
| 命令执行 | **退出状态**及任务要求的结果检查 |

> 证据必须来自工具/页面的客观返回，不能来自模型自述。

### 5.2 【修订 4】三类键与持久化认领

**问题**：第一稿用 `task_id + plan_version + step _id` 作为"继续令牌"，**永久只放行一次**，会同时挡住后续**合法重试**；且未规定数据库如何原子认领、拒绝并发、作废旧执行者。

**修订：把三种身份彻底分开。**

| 键 | 定义 | 作用 | 生命周期 |
|---|---|---|---|
| **请求幂等键 `request_id`** | 由**调用方/客户端**生成、**重发时不变**的稳定标识（如 `req_<uuid>`） | 识别"同一次请求"，含**响应丢失后的重发** | 重发不变；仅换新请求才换新值 |
| **派发幂等键 dispatch key** | `task_id + step_id + attempt_seq` | 防止**同一执行尝试**被重复派发 | 每次新执行尝试产生新键 |
| **步骤身份 step identity** | `step_id = task_id + plan_version + index` | 稳定标识"这是哪一步" | 同一计划版本内不变；改计划 → 新版本新 ID |
| **执行尝试身份 attempt identity** | `attempt_id`（任务内唯一）+ `attempt_seq` 单调递增 | 区分同一句话的**多次真实执行** | 每次重跑 +1，历史保留 |

**持久化原子认领（单事务五步）**：

对"继续 / 启动"请求，**在同一事务内**完成以下五步；任一步失败整体回滚：

1. **请求去重（按 `request_id`）**：`INSERT INTO requests(request_id) ON CONFLICT DO NOTHING`。**冲突** → 该请求是**重发** → **复用首次结果并直接返回**，不再往下执行。
2. **可执行状态检查（允许列表）**：仅当任务/步骤状态 ∈ **允许启动集合** `{pending, interrupted, failed(重试), needs_check(核对后可重跑)}` 时放行；否则拒绝（含"执行中"）。
3. **Attempt 分配**：读取该步骤 `max(attempt_seq)+1`，生成**新 Attempt**（`status=pending`）。
4. **状态认领**：在同一事务内 `UPDATE steps SET status='running', active_attempt_id=<新 attempt> WHERE step_id=? AND status IN (允许集合)`，并把任务置 `running`、绑定 `active_attempt_id`。**这是关键一步**——把"已被认领"写进持久状态；若影响行数 ≠ 1（状态已被他人抢先改走）则**整体回滚**。
5. **epoch 更新（乐观锁）**：`UPDATE tasks SET executor_epoch=executor_epoch+1 WHERE task_id=? AND executor_epoch=?`（**要求与当前值相等**），不等则回滚重试。

**要点**：

- 因为 `request_id` 与 `attempt_id` **解绑**：第一次启动成功但响应丢失时，客户端**重发携带同一个 `request_id`** → 第 1 步键冲突 → **挡在启动之前**（旧稿用 `attempt_seq` 会把重发误判为新请求而漏挡）。
- **合法重试**使用**新的** `attempt_seq`（→ **新的**派发幂等键），并由执行器/用户发起**新的 `request_id`**；两者共同保证"**重发被挡、重试放行**"。
- **原子认领防并发**：因为第 4 步把任务/步骤置为 `running` 并绑定 `active_attempt_id`，**两个不同 `request_id` 的并发启动只有一个能提交**：第二个在同一事务的"可执行状态检查 / 状态认领"处读到已非允许状态（`running`）而回滚，不会创建第二个 Attempt。（旧稿只有前四步时，两个 `request_id` 可能依次通过，各自创建 Attempt，即使后者的写入被 fencing 拒绝，**已派发的工具仍可能执行**。）
- **fencing**：`executor_epoch` 单调递增，执行器写检查点/结果须携带该 epoch，**要求 `epoch` 等于当前值**（与认领的乐观锁条件一致）；不等于当前值的写入被拒绝，使崩溃后旧执行者的迟到写入失效。

> 现有 `localtools.resolve` 对重复 `call_id` 的幂等（`localtools.py:565`）是**进程内**幂等，仅作参考，不能承担跨重启的请求去重。

### 5.3 工作重复去重（跳过已完成且结果仍有效）

判据：该 `step_id` 已 `已完成`，其 `result_ref` 仍可按 `result_digest` 校验通过，**且**其 `input_fingerprint` 未变化（§3.4）。三者同时满足才跳过。

### 5.4 【修订 5】跨崩溃的工具执行证据与旧执行者确认

**问题**：第一稿依赖 `localtools._DONE` 查询既有执行，但它只是**内存中的 call_id 集合**（`localtools.py:402`），**不保存结果**，且超过 500 会清空，**重启后消失**。此外"文件尚不存在"**不能**证明旧客户端稍后不会完成写入。

**修订：把执行意图持久化，并规定派发顺序与确认策略。**

**派发顺序（三段式，缺一不可）**：

```
① 持久化执行意图（intent）→ ② 派发给客户端 → ③ 收到结果后持久化（result）
```

- **① 执行意图** 写入任务库：`request_id`、`tool`、`args_digest`、`dispatch_key`、`dispatched_at`、目标客户端身份、`executor_epoch`。**必须在派发之前落盘**——崩溃后才可据此判断"是否发出过"。
- **② 派发**：把 `dispatch_key`（必要时含 `request_id`）一并下发给客户端。
- **③ 结果** 落盘：`result_ref`、`result_digest`、`status`。

**旧执行者确认**：

1. 恢复时，对**已落盘 intent 但无 result** 的步骤，**先查询**客户端/服务的实际状态，不直接重发。
2. **客户端必须把每个 `dispatch_key` 的执行记录持久化**（落盘，**跨客户端重启仍可查**），并对同键的重复意图**不得**重复执行副作用，只回报既有结果。（仅存在内存里不算数。）
3. **查询必须返回以下固定状态集之一**（不得返回集合外的值）：

| 客户端状态 | 含义 | 是否允许大脑重试 |
|---|---|---|
| `未接收` | 明确从未收到该 intent | **允许**（补发） |
| `已接收` | 收到但尚未开始 | **允许**（补发，客户端按键幂等） |
| `执行中` | 正在执行 | **不允许**；等待或转 `待核对` |
| `已完成` | 已执行并已有结果 | **不重试**；取回结果 |
| `已确认停止且结果已核对` | 已停止且结果已核对 | 依核对结论（T7/T8/T8a） |
| `未知` | 查不到 / 客户端已重启 / 无法判定 | **不允许直接重跑**；一律 `待核对` |

4. **"未完成" ≠ 可重跑**：`执行中` 表示可能仍在运行；`未知`（含客户端重启后**查不到**）**不能**证明从未执行。
5. **fencing 的边界**：`executor_epoch` 只能拒绝**迟到的数据库写入**，**不能**阻止旧客户端继续产生**文件等外部副作用**。外部副作用必须靠 **客户端按 `dispatch_key` 的去重 + 读后核对**兜底。
6. **无法确认旧操作是否结束**时：一律 `待核对`，**禁止**直接重发写操作，直到客户端给出上述状态之一。
7. **"文件尚不存在"不作为"未写入"的凭据**：旧客户端可能稍后完成写入；必须依赖 `dispatch_key` 让迟到重复写入被客户端拒绝，实现"至多一次 + 核对补偿"。

> 结论：跨崩溃的执行证据 = **持久化的 intent + 客户端按幂等键的确认**，而不是内存 `_DONE`。

## 六、第六步：故障恢复决策表（含预算与取消）

### 6.1 主决策表

| 故障位置 | 恢复后的第一步 | 默认处理 |
|---|---|---|
| **工具请求发送前退出** | 检查是否仍 `待执行`（无 intent 记录） | 可以启动 |
| **请求发出后失去确认** | 查询 intent + 客户端状态 + 实际结果 | **不直接重发**（§5.4） |
| **工具完成后、记录落盘前退出** | 检查完成证据（intent 已落、result 未落） | 确认完成或转 `待核对` |
| **已完成步骤的相关输入变化** | 重算 `input_fingerprint`（§3.4） | 重新验证 + 标记下游影响 + 新计划版本 |
| **等待审批时断线** | 检查当前权限及审批有效性 | **不沿用过期批准**（T6a） |
| **达到执行预算** | 读取最后的可靠检查点 | 保留进度，等待明确继续 |
| **用户取消后重启** | 读取取消状态 | 保持取消 |

### 6.2 三个不同事件

| 事件 | 后台任务状态 | 恢复动作 |
|---|---|---|
| **页面关闭** | 后台任务**可能仍在运行** | **先观察现有执行**，不能再启动一份 |
| **模型请求中断** | "请求发出后失去确认" | 按 6.1 第二行：核对、不直接重发 |
| **Brain 退出** | 进程内存态全丢（`results`/`hist` 只在内存） | 从任务库读检查点，按状态机恢复 |

### 6.3 【一般修订 1】任务预算契约

**问题**：样例直接套用 FC 的 24 轮 / 270s，但首期排除了 FC。

**修订：任务预算独立定义，与 FC 无关。**

| 预算项 | 含义 | 默认 | 继续时 |
|---|---|---|---|
| `max_steps` | 单次执行允许的最大步骤数 | 8 | 与已执行步骤累计比较 |
| `max_attempts_per_step` | 单个步骤允许的最大尝试次数 | 3 | 按 `attempt_seq` 累计，**不重置** |
| `budget_seconds` | 单次执行的墙钟软上限 | 600s | 逐次累计 |
| `deadline` | **绝对截止时间**，任务创建时设定 | 创建时刻 + 时长 | **继续时不变，不重置** |
| `consumed` | 已消耗量（步骤/尝试/秒） | — | **持久化，继续时接着算** |

规则：

① **预算独立于 FC 的 24/270**。
② `deadline` 在继续时**不延长**。
③ **预算耗尽后"继续"不能单独恢复执行**：必须先取得**一次新的预算授予**（记录"预算授予"事件）；未获新预算时，"继续"按钮**只展示进度、不启动执行**。
④ **预算授予更新哪些上限**：仅更新**上限字段** —— `max_steps`、`max_attempts_per_step`、`budget_seconds`、`deadline`。
⑤ **哪些累计消耗保留**：`consumed`（步骤数 / 尝试数 / 已用秒）**一律保留、不清零**，新上限与已消耗量比较。
⑥ 达到预算 = 正常中断，保留进度。

### 6.4 【一般修订 2】取消语义：调度停止 ≠ 工具实际停止

**问题**：任务取消后，可能仍有客户端操作正在收尾；不能据此宣称副作用已停止。

**修订：区分两个概念。**

| 概念 | 含义 | 记录 |
|---|---|---|
| **cancel_requested（调度停止）** | 大脑停止**派发新的**步骤/尝试 | 任务/步骤置取消意图 |
| **tool_stopped（工具实际停止）** | 仅在**客户端确认** in-flight 操作已结束 | 由客户端确认写入 |

规则：① 任务卡片在获得 `tool_stopped` 确认前，**不得**声称"副作用已停止"；② 已派发未确认的操作维持 `待核对`；③ 取消是**终态**（T11/T12），但"实际停止"是独立事实，须分别记录。

## 八、第八步：故障推演表（8 场景）

每个场景写：① 重启后读到什么记录；② 可确认的事实；③ 下一步允许执行什么；④ 怎样避免重复；⑤ 界面怎样说明。

### 场景 1：启动前退出（S1 尚未开始）
- ① Task `pending`，S1 `待执行`，**无 intent 记录**。
- ② 从未发出任何工具请求。
- ③ 可安全启动 S1（T1）。
- ④ 无已发出请求，无需去重。
- ⑤ "尚未开始 / 中断位置：查找日志"，提供［继续任务］。

### 场景 2：请求发出后断连（S2 已发请求，未收结果）
- ① S2 `待核对`；有 **intent** 记录，无 result。
- ② 请求**已发出**；**结果不确定**（不是"未执行"）。
- ③ **先查询 intent + 客户端状态**，不得直接重发（§5.4）。
- ④ 以 `dispatch_key` 查询既有执行；客户端按幂等键拒绝重复副作用。
- ⑤ "读取结果尚未确认，需要先检查"，给［核对结果］［查看执行记录］。

### 场景 3：工具完成但检查点未落盘（S4 写文件成功，落盘前崩溃）
- ① S4 `执行中`→应为 `待核对`；有 intent，无 result；磁盘**可能已有**目标文件。
- ② 目标路径已知；文件是否存在需现场读取确认。
- ③ 读目标文件核对 → 匹配则 T7 补记完成；不匹配则维持 `待核对`。
- ④ **不重发写入**；以"读后核对"为唯一判据；客户端按幂等键拒绝迟到重复写。
- ⑤ "报告保存结果尚未确认"，给［核对结果］。

### 场景 4：重复 / 并发点击"继续"
- ① 同一**请求幂等键**出现两条启动意图。
- ② 这是**请求重复**，不是两次真实工作。
- ③ 唯一约束下**仅一个插入成功**；第二个复用首次结果（§5.2）。
- ④ 幂等键 + `TASK_LOCK` + 状态校验共同防并发。
- ⑤ 第二次点击返回"任务已在继续中"。

### 场景 5：恢复前文件被修改（**按 §3.4 重写**）
- ① S2 `已完成`，记录了 `input_fingerprint`；重算源文件指纹**与记录不一致**。
- ② 输入已变化 → S2 结果**失效**，下游 S3/S4 **受影响**。
- ③ 生成 `plan_version+1`，重新分析；旧版本历史保留（T14/T14a）。
- ④ 以**输入指纹**（不是 `result_digest`）判失效。
- ⑤ "源文件已变化，需要重新分析"，给［继续任务］。

### 场景 6：恢复前授权被收回
- ① Task `已中断`；当前授权已变更。
- ② 执行时授权快照 ≠ 当前授权。
- ③ 恢复时**重查当前权限**；无权限则允许集为空（fail closed）。
- ④ 不沿用旧批准；`waiting_user` 未消费的审批作废。
- ⑤ "授权已变化，无法继续原步骤"。

### 场景 7：达到轮次 / 时间预算
- ① `consumed` 显示已达 `max_steps`/`budget_seconds` 或越过 `deadline`。
- ② 被预算闸中断，**非故障**；已完成步骤结果仍在。
- ③ 从**最后可靠检查点**继续；`deadline` **不延长**（§6.3）。
- ④ 已 `已完成` 且有效的步骤跳过。
- ⑤ "已达本次预算，已完成 X/Y 步"，给［继续任务］。

### 场景 8：用户取消后重启
- ① 任务 `已取消`（终态，已落盘）；另有 `cancel_requested` / `tool_stopped` 区分（§6.4）。
- ② 取消是用户明确意图。
- ③ **不自动重启**；保持取消。
- ④ 取消终态优先级最高，汇总规则不可翻回。
- ⑤ "已取消"，仅可查看记录。

## 九、故障验收表（阶段一交付物）

| # | 场景 | 期望状态 | 验收断言 |
|---|---|---|---|
| AC-1 | 启动前退出 | `pending` | 无 intent 记录；可安全启动；无副作用 |
| AC-2 | 请求发出后断连 | `待核对` | 不得记为"未执行/失败"；不得直接重发；提供核对入口 |
| AC-3 | 工具完成、落盘前退出 | `待核对` 或 `已完成` | 以读文件核对为判据；不得重发写操作 |
| AC-4 | 重复点击继续 | 单次有效启动 | 第二次复用首次；不新建 Attempt |
| AC-5 | 恢复前文件被修改 | 受影响步骤重新验证 | **用 input_fingerprint 判失效**；下游标记受影响；生成新计划版本 |
| AC-6 | 恢复前授权被收回 | 按当前权限执行或拒绝 | 恢复时重查权限；不沿用过期批准 |
| AC-7 | 达到预算 | 保留进度 | 读最后可靠检查点；已完成跳过；`deadline` 不延长 |
| AC-8 | 取消后重启 | 保持 `已取消` | 终态不可翻回；不自动重跑 |
| AC-14 | 两个不同 `request_id` 并发启动同一任务 | 单次有效执行尝试 | 状态认领、Attempt 创建、epoch 更新、请求结果关联**必须同一事务一起提交或回滚**；仅一个生效 |

**断言级细则**：

1. **超时不得记为未执行**（AC-2）。
2. **模型自述不构成完成证据**（全部）。
3. **待核对不得显示完成**（AC-2/AC-3）。
4. **写操作至多一次 + 核对补偿**（AC-2/AC-3/AC-4）：靠 `dispatch_key` + 读后核对。
5. **权限每次恢复必查**（AC-6）：fail closed。
6. **取消不可逆**（AC-8）。
7. **历史只追加**（全部）。
8. **合法重试不被去重挡住**（AC-4）：重试用新 `attempt_seq` → 新幂等键。
9. **旧执行者写入被拒**（AC-2/AC-3）：`executor_epoch` fencing。
10. **输入变化传播下游失效**（AC-5）。
11. **入口可达**（全场景前提）：任务仅经 `/api/task/start` 创建；聊天入口不产生可恢复任务。
12. **重发被挡**（AC-4）：启动成功但响应丢失后的**重发**携带同一 `request_id`，被唯一约束挡住，不产生第二次启动。
13. **状态集固定**（AC-2/AC-3）：客户端查询只返回 §5.4 的六种状态；`执行中`/`未知` 不允许直接重跑。
14. **原子状态认领**（AC-14）：两个不同 `request_id` 并发启动同一任务，只能有一个有效执行尝试；状态认领、Attempt 创建、epoch 更新与请求结果关联必须一起提交或回滚。

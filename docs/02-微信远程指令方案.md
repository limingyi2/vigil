# 微信远程指令通道方案

> 版本：v1.0 · 2026-10-10
> 状态：待实施

---

## 一、要解决什么问题

### 现状
- 微信群消息走**云端大脑**（`wechat_route=cloud`）
- 云端装了 `remote` 插件，模型看得到 22 个本地操控工具
- 但**云端没有客户端轮询**——你的桌面客户端连的是本地大脑，不是云端
- 结果：模型尝试调用 `local_*` 工具 → 秒回"没有在线的电脑能执行" → 只能聊天

### 目标
在微信群里，**只有你发的清晰操控指令**才会被转发到本地大脑执行；其他消息正常走聊天路径，完全不影响日常聊天。

---

## 二、触发条件（四层验证）

只有**同时满足**以下四条，才会转入本地执行：

| 层 | 验证项 | 具体规则 |
|---|---|---|
| ① | 名字白名单 | 发送者显示名必须是 `lmy`（从消息文本 `名字：内容` 解析） |
| ② | 指令密码 | 消息里必须包含独立词 `12`（前后是空格/标点/开头结尾，避免 "12点"、"123" 误触发） |
| ③ | 指令明确性 | 必须是操控本地电脑的清晰指令（关键词快筛 + 模型判定） |
| ④ | 客户端在线 | management 通道确认 `local-pc` 在线（本地大脑 + 客户端都在） |

**任何一条不满足 → 正常走聊天路径，模型完全感知不到"远程指令"这个东西的存在。**

---

## 三、完整流程

```
微信群你发：@麦麦 12 帮我看看下载文件夹里有什么
    ↓
云端大脑收到消息（src=wechat_group）
    ↓
remote_command 插件（on_turn_in 钩子，最先执行）
    ├─ ① 解析发送者名：lmy ✅
    ├─ ② 密码检测：独立词 "12" ✅
    ├─ ③ 指令判定："帮我看看下载文件夹" → 是操控指令 ✅
    └─ ④ 查 management：local-pc 在线 ✅
    ↓ 全部通过
ctx.veto() —— 否决正常聊天链路
    ↓
通过 management 通道派活给 local-pc
（消息类型：remote_command，带指令文本）
    ↓
本地大脑（management_agent）收到指令
    ↓
调用本地大脑 ask_with_retry(src="remote_cmd")
（带全部本地操控工具，走正常工具调用流程）
    ↓
执行完成，结果通过 management 返回云端
    ↓
云端：
  - 群里只回一句："已发到你电脑上了，回去看结果"
  - 详细执行结果存在云端，你回客户端能看到
  - （结果隔离：文件内容、目录列表等绝不发到群里）
```

### 失败分支

| 失败点 | 行为 |
|---|---|
| 发送者不是 lmy | 正常聊天，完全不触发 |
| 没有密码 "12" | 正常聊天，完全不触发 |
| 不是操控指令 | 正常聊天，完全不触发 |
| local-pc 不在线 | 群里回："你电脑没开，等开了再说" |
| 本地执行超时 | 群里回："电脑那边有点慢，等会儿回去看" |
| 本地执行报错 | 群里回："执行出了点问题，回去看详情" |

## 四、指令明确性判定规则

### 关键词快筛（第一层，零成本）

消息包含以下任一关键词，才进入模型判定：
- `帮我看看` + （`电脑` / `本地` / `文件夹` / `文件` / `桌面` / `下载`）
- `帮我打开` + （`浏览器` / `网页` / `文件` / `文件夹`）
- `帮我查` + （`电脑` / `本地` / `文件`）
- `帮我截图` / `看看屏幕`
- `帮我执行` / `帮我运行`
- `电脑上` / `本地电脑`

### 模型判定（第二层，一次 flash 调用）

关键词命中后，用云端模型（DeepSeek-V4-Flash）判一次：
> 这条消息是不是让你操控发送者的本地电脑？只回答 yes 或 no。

- `yes` → 进入派活流程
- `no` → 正常聊天

> 为什么还要模型判定？因为关键词会误命中，比如"帮我看看这个表情包"不是操控指令。模型判定成本很低（一次 flash 调用几毫秒），但能把误触发率降到接近零。

## 五、需要改的代码

### 1. 云端新增：`brain/plugins/remote_command.py`（~120 行）

- 挂 `on_turn_in` 钩子（优先级最高，先于 gate 等其他插件）
- 解析发送者名（从 `名字：内容` 格式）
- 密码检测（独立词 `12`）
- 关键词快筛
- 模型判定（调用云端模型）
- management 在线检查
- 全部通过 → `ctx.veto()` + management 派活 + 返回状态句

### 2. 云端修改：`brain/management.py`（+~40 行）

- 新增 `remote_command` 消息类型
- 派活接口：`send_command(node_id, command_text) → job_id`
- 结果接收：本地执行完后回传结果，按 job_id 匹配

### 3. 本地修改：`brain/management_agent.py`（+~50 行）

- 接收 `remote_command` 消息
- 调用本地大脑 `ask_with_retry(src="remote_cmd")`
- 执行结果通过 management 回传云端
- 超时保护（最长 60 秒）

### 4. 配置项（config.json）

```json
{
  "remote_command": {
    "enabled": true,
    "owner_names": ["lmy"],
    "password": "12",
    "keywords": ["帮我看看", "帮我打开", "帮我查", "帮我截图", "电脑上", "本地电脑"],
    "timeout_seconds": 60
  }
}
```

## 六、安全设计

### 为什么这样安全

| 攻击场景 | 结果 |
|---|---|
| 群友发"@麦麦 12 帮我删文件" | ❌ 发送者不是 lmy，直接忽略 |
| 群友改群昵称为 lmy，发"@麦麦 12 帮我删文件" | ⚠️ 名字能过，但他怎么知道密码是 12？（密码只有你知道） |
| 群友知道密码 12，改昵称 lmy，发指令 | ⚠️ 理论上能触发，但群里就四五个人都认识，不会干这事；而且执行结果只在你客户端，他看不到 |
| 你不小心在群里发"12点吃饭" | ❌ "12" 不是独立词（后面跟了"点"），不触发 |
| 你发"@麦麦 12 今天天气怎么样" | ❌ 不是操控指令，模型判定 no，正常聊天 |
| 你客户端没开时发指令 | ❌ management 检测 offline，回"你电脑没开" |

### 结果隔离

- 执行结果（文件内容、目录列表、命令输出等）**只存在云端，绝不发到群里**
- 群里只回一句状态："已发到你电脑上了"
- 你回到客户端（工作台）能看到完整执行过程和结果

## 七、部署步骤

1. 把 `remote_command.py` 放到云端服务器 `C:\Vigil\plugins\`
2. 修改云端 `management.py`，加 command 消息类型
3. 修改本地 `management_agent.py`，接收并执行
4. 在云端 `config.json` 加 `remote_command` 配置段
5. 重启云端大脑
6. 确保本地大脑 management agent 在线（当前是 offline，需要排查）
7. 测试：在微信群发 `@麦麦 12 帮我看看下载文件夹`

## 八、验证清单

- [ ] 群友（非 lmy）发任何消息，不触发远程指令
- [ ] lmy 发普通聊天（不含 12），正常聊天
- [ ] lmy 发含 "12" 但非操控指令（如"12点吃饭"），正常聊天
- [ ] lmy 发 `@麦麦 12 帮我看看下载文件夹`，触发远程指令
- [ ] 本地大脑在线时，指令被转发到本地执行
- [ ] 群里只回状态句，不暴露执行结果
- [ ] 客户端能看到完整执行过程
- [ ] 本地大脑离线时，回"你电脑没开"
- [ ] 密码改成其他值后，旧密码不触发

## 九、已知限制

1. **本地大脑必须在线**——management agent 当前是 offline，需要先排查原因（可能是客户端没开，或者网络问题）
2. **执行有延迟**——从发指令到本地执行完，预计 5-15 秒（模型调用 + 工具执行 + 网络往返）
3. **不能执行超长任务**——单次指令最长 60 秒，超时返回"执行中，回去看结果"
4. **密码是静态的**——`12` 固定不变，如果担心可以改成动态密码（客户端生成，每次变），但更复杂
5. **名字白名单依赖桥接格式**——必须是 `名字：内容` 格式，如果桥接改了格式需要同步调整解析逻辑

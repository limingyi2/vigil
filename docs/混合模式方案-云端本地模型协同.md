# 混合模式方案 v2 — 云端大模型 + 本地模型协同（优化版）

> 基于原《混合模式方案》修订。改动动机：原方案有三个落地坑——
> ① 模型名写死且疑为笔误；② 云端大脑够不着家里的 Ollama（网络拓扑没解决）；
> ③ 工具注册没走项目现有的 TOOL_SPECS 机制（CHANGELOG 10-08 刚修过同类断链）。
> 本版已按项目实际代码（brain/localtools.py、brain/plugins/remote.py、brain/tools.py）逐条核对。

## 一、v2 改了什么（对照表）

| # | 原方案 | v2 |
|---|--------|-----|
| 1 | 模型名写死 `qwen3.8:27b`（此版本号不存在） | 模型名放配置，启动时用 `ollama list` 校验，对不上就提示 |
| 2 | brain 直连 `http://127.0.0.1:11434` | **云端 brain 走 localtools 派活给 PC 客户端执行**；本地 sidecar brain 才允许直连（快路径） |
| 3 | 新建插件注册 local_model 工具 | **只改 `localtools.REMOTE_TOOLS` 一处**，plugins/remote.py 自动生成 TOOL_SPECS/TOOLS/路由，不新增插件 |

| 5 | 错误降级「Ollama 没开 → 降级云端」 | 沿用 localtools 已有的在线检测（POLL_STALE）+ 客户端报错文案约定（可重试/别重试），模型自动转述 |

## 二、设计目标（保留）

- 聊天只走云端（人设、拟人化、复杂推理）
- 脏活累活给本地模型：批量文件、代码草稿、长文摘要、数据清洗、本地文件问答
- 一个开关控制，用户无感知
- **v2 新增**：无论消息从哪个渠道进来（微信/App/PC），只要当前大脑需要调本地模型，链路都必须走得通

---

## 三、修订后的架构

```
用户（微信 / App / PC）
        │
        ▼
┌──────────────── Brain（云端或本地 sidecar）────────────────┐
│  云端主模型（DeepSeek/Mimo）                                │
│    · 聊天/人设/推理/工具决策                                │
│    · function calling 看到 local_model 工具                 │
└──────────────────────┬──────────────────────────────────────┘
                       │ 调用 local_model
                       ▼
        ┌── localtools.call("local_model", ...) ──┐
        │  · clearance() 按渠道/风险把关            │
        │  · _LAST_POLL 在线检测，没人轮询就秒回     │
        │  · 排队 / 取消 / 审计 / 统计 全部复用      │
        └──────────────────┬───────────────────────┘
                           │ 塞进队列，阻塞等结果
        客户端 1.5s 轮询 GET /api/device/poll（声明能力含 local_model）
                           ▼
┌───────────────── PC 客户端执行器（新增分支）─────────────────┐
│  · 调本机 Ollama（http://127.0.0.1:11434）                 │
│  · Ollama 没起 → 报错文案回传，主模型转述并降级              │
│  · POST /api/device/tool_result 送回结果                    │
└─────────────────────────────────────────────────────────────┘
                           ▼
                    Ollama（用户已下载的模型）

快路径（P1 可选）：当 brain 以本地 sidecar 身份跑在同一台 PC 上时，
local_model 可直接调 Ollama，省掉一次轮询往返（≈1.5s）。单代码路径先跑通，再优化。
```

**为什么不直连**：README 已写明——云端的大脑够不着家里的模型，中间必须走隧道。
而 localtools 那条「服务端排队 → 客户端轮询取走 → 执行 → 送回」的通道，正好就是现成的隧道，
且自带认领规则（谁有能力谁认领）、风险把关、取消、审计。原方案「不用 WS 用轮询」的论证同样适用。

## 四、任务分配策略（保留原表，微调）

走本地：批量文件处理、代码生成/审查草稿、长文本摘要、本地文件问答、数据清洗、简单分类打标签。
必须云端：人设对话、复杂推理/数学、创意写作、工具调用决策、多轮规划。

**v2 微调**：
- 「本地文件问答」从白名单默认开启改为默认关闭（它要先读文件，链路长，P2 再做）。
- 「代码生成」产出的脚本若要**执行**，执行动作走现有 local_exec，按原风险档单独审批——
  local_model 本身只产出文本，标 `risk: "safe"`。

---

## 五、调度逻辑（两层，保留）

**第一层 规则预判（零成本）**：明显的批量/整理/转换类请求直接派本地。
- v2 注意：这层只在「开了混合模式」时生效，且**不要绕过人设系统提示词**——
  规则层只做「建议走 local_model 工具」的提示注入，最终仍由主模型发工具调用，避免绕过审批和审计。

**第二层 主模型判断**：function calling 决策，与现有一致。

## 六、实现细节（按真实代码核对过）

### 6.1 配置（brain/config/config.json 加一段）

```json
"hybrid": {
  "enabled": false,
  "ollama_base": "http://127.0.0.1:11434",
  "model": "<填 ollama list 里的实际名字>",
  "max_tokens": 4096,
  "keep_alive": "10m",
  "whitelist": ["file_process", "code", "summarize", "data_clean"]
}
```

### 6.2 服务端只改 localtools.py 一处

在 `REMOTE_TOOLS` 登记表里加：

```python
"local_model": {
    "desc": "把任务交给你电脑上的本地模型处理。适合：批量文件处理、写代码草稿、长文摘要、"
            "数据清洗。不适合：聊天、复杂推理、创意写作。本地模型看不到聊天上下文，"
            "task 里要把任务说完整。",
    "params": [
        ("task", "给本地模型的完整任务描述", True),
        ("max_tokens", "最大输出，默认 4096", False),
    ],
    "arg_param": "task",
    "danger": False,
    "risk": "safe",
    "group": "system",
},
```

加完之后**自动获得**（plugins/remote.py 是遍历 REMOTE_TOOLS 生成的）：
- TOOL_SPECS → 主模型 function calling 能直接看到并调用
- TOOLS → `[tool:local_model:...]` 标签路径兼容
- `/api/device/poll` 派发 + `/api/device/tool_result` 回传路由
- clearance() 渠道把关（群聊只见 safe 档——local_model 是 safe，群里也能用）
- 在线检测：客户端没轮询时秒回「没有在线的电脑…让他打开 Vigil 客户端」

两个小补丁：
1. `call()` 里读 `spec.get("wait")` 覆盖默认超时——本地推理比 shell 慢，建议 180s。
2. `specs()` 里按配置裁剪：`hybrid.enabled` 为 false 时不暴露 local_model（模型看不见=不会乱许诺）。

### 6.3 客户端执行器（轮询处理器加一个分支）

```pseudo
if call.name == "local_model":
    if not hybrid.enabled: return err("混合模式已关闭")
    r = POST {ollama_base}/api/chat {model, prompt: task, stream: false, keep_alive}
    if 连不上: return err("Ollama 没在跑（127.0.0.1:11434 连不上）【可重试：启动 Ollama 后再试】")
    return ok(r.text)
```

启动时（或开开关时）`GET /api/tags` 校验配置里的 model 在已下载列表里，不在就在设置页红字提示。

### 6.4 客户端设置页（pages.js，仿照「云端同步」那张卡）

连接与系统 → 混合模式：开关 / 模型名（从 /api/tags 拉下拉列表）/ keep_alive / 白名单勾选 / 状态行（已加载·空闲·推理中）。

### 6.5 与 model_hub 的关系

model_hub 管的是「聊天主模型选哪家」，不动它。P2 可选：把 ollama 注册为一个只读 provider，
让模型选择器里能展示本地模型——纯展示，不改聊天路由。

## 七、上下文与显存（保留要点）

- 本地模型独立上下文，不与主模型共享；主模型只看到任务描述+结果
- 大文件：执行器侧分片（按段落/章节），逐片处理后合并
- 结果回传前截断/摘要（建议 ≤ 2000 token），避免撑爆主模型上下文
- 显存：keep_alive 配置化（默认 10m）；混合模式关闭时可调 `ollama stop` 立即卸载

## 九、风险与应对（修订表）

| 风险 | 应对 |
|------|------|
| 本地模型输出质量差 | 白名单只放简单任务；主模型审核/润色后再回复 |
| PC 客户端不在线 | localtools 已有的 POLL_STALE 检测，秒回并提示打开客户端 |
| Ollama 没启动 | 执行器报错文案回传，主模型转述；用户启动后重试 |
| 本地推理慢 | wait 提到 180s；超时文案标「别重试」；设置页显示推理中 |
| 显存冲突（游戏+模型） | keep_alive 自动卸载；设置页提供「立即卸载」 |
| 主模型不主动调 | 系统提示词里写明批量/代码/摘要优先 local_model（插件 desc 里已写引导语） |
| 群里被滥用 | risk=safe 群聊可见，但 local_model 只产文本不执行；执行类仍走 local_exec 审批 |

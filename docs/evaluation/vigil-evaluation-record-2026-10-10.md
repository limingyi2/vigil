## 二、Eval Harness 基础测试

在隔离 workspace 中，以确定性脚本模拟两组执行路径。共选 F01、M01、P01、S01 四道题，每题两组，8/8 通过。

测试证明了任务 fixture、Oracle、日志与沙箱的基础流程可用。由于未调用真实 Brain 或模型，不能把这份通过率解释为 Agent 能力或 Planner 效果。

这一阶段审计的代码版本为 `4e3b62dd8d05e009b33e7bd3966f9a50d150e2eb`，不代表后续所有实验均使用该版本。审计还发现 Planner 的工具执行路径当时没有完整传递 `src` 与任务级 `allowed_tools`；后续测试应核实修复后的执行层权限校验。

## 三、MiMo Planner 对照实验

模型为 `mimo-v2.6-flash`。比较 A_direct（Planner 关闭）与 B_current（已有 Planner 加条件式 Checker），各运行 8 个任务，每个 run 使用独立的配置、会话和 workspace。

| 指标 | A_direct | B_current |
|---|---:|---:|
| Oracle 通过数 | 3/8 | 3/8 |
| 模型请求次数 | 19 | 17 |
| 输入 tokens | 17,734 | 10,130 |
| 输出 tokens | 1,678 | 1,962 |
| 工具调用次数 | 18 | 12 |
| 平均耗时 | 11.83 秒 | 14.48 秒 |

共完成 16 个 task-run、36 次真实模型请求。B_current 的 5 个符合规划条件的任务都生成了有效计划，未发生 fallback；Checker 调用 1 次，没有触发修正。

现有结果表明，本轮 B_current 使用了较少的输入 tokens 和工具调用，但平均耗时更长，成功率没有提升。部分任务的题面及 Oracle 存在问题：F02 强制要求固定答案格式，M01 缺少明确修改目标，P02、L04 和 S02 把文件发现与任务目标混在一起。因此原始 3/8 保留，但目前不能据此认定 Planner 没有价值。

## 四、Qwen 27B 首轮高难度测试

模型为 `qwen27b-efficientthink:latest`，27.3B 参数，IQ3_S 量化，运行在 Windows 本地 Ollama。

| 题目 | 原始得分 | 主要现象 |
|---|---:|---|
| H1 复杂规划 | 15/20 | 能给出基本合理的计划 |
| H2 跨文件修复 | 3/25 | patch 输出不完整 |
| H3 工具选择与权限 | 0/20 | thinking 占用生成预算，最终 JSON 没输出完整 |
| H4 长日志根因 | 0/15 | 没按约定格式输出 JSON |
| H5 状态压缩与恢复 | 18/20 | 摘要部分较好，但后续格式切换有问题 |
| 合计 | 36/100 | 仅代表首轮原始配置表现 |

首轮成绩不应视为模型稳定能力评分。原始分数来自当时的报告截图；本整理没有重新取得完整首轮原始回答逐题复核。

## 五、Qwen 参数调整与复测

扩大输出预算、改进结构化输出后，表现明显改善。

- H2：将 `num_predict` 提高至 2048，修复代码完整生成，预写单测 15/15 通过。单测通过数和原先 3/25 评分不是同一指标。
- H3：复测的三种配置均输出合法 JSON；使用 `format="json"` 时，单次输出约 88 tokens，对照配置约 199 tokens。这个对照不能直接推广到所有任务。
- H5：第二阶段格式切换报告为 7/8；第一阶段在 1024 生成预算下仍出现过长度截断。

可以确认 H2、H3 的首轮失败受到输出预算和思考过程显著影响。原报告所称“80% 至 90% 的低分属于配置问题”没有统一评分依据，不作为正式量化结论。H4 仍缺少同口径的复测结论。

## 六、长上下文能力与状态压缩

最初的上下文专项测试记录如下：

| num_ctx 设置 | 实际输入 tokens | 事实检索与多跳 | 状态保持率 |
|---:|---:|---|---:|
| 8,192 | 4,098 | 该次正确 | 0.54 |
| 16,384 | 8,194 | 该次正确 | 0.54 |
| 24,576 | 12,290 | 该次正确 | 0.54 |
| 32,768 | 16,386 | 该次正确 | 0.54 |

状态压缩测试中，早期已完成事项召回率约 0.17、失败事项召回率为 0。Qwen 可以帮助生成摘要，但不能取代 Vigil 的权威任务状态存储；已完成、失败、待执行和测试结果应由确定性代码保存。

这轮测试曾因为实际输入长度恰好约为 `num_ctx` 的一半，误判模型有效上下文上限为 16K。下一轮独立诊断已经推翻这一判断。

## 七、Ollama 上下文独立诊断

固定 `num_ctx=32768`、`num_predict=256`、`temperature=0`、`format="json"` 和 `think=false`，使用动态校准构造输入，并在头部、中部、尾部植入可验证标记。

| 目标输入 tokens | 实际输入 tokens | 标记召回 | 墙钟时间 |
|---:|---:|---|---:|
| 4K | 3,911 | 正确 | 9.13 秒 |
| 8K | 7,902 | 正确 | 14.84 秒 |
| 12K | 11,901 | 正确 | 21.79 秒 |
| 16K | 15,879 | 正确 | 33.71 秒 |
| 18K | 17,864 | 正确 | 33.70 秒 |
| 20K | 19,852 | 正确 | 37.24 秒 |
| 24K | 23,844 | 正确 | 45.76 秒 |
| 28K | 27,847 | 正确 | 54.58 秒 |

在最高档，头中尾标记和所有已植入的边界标记都正确召回；没有出现 16K 输入计数封顶、OOM 或请求超时。模型定义中也没有预设 16K 的 `num_ctx` 上限。

因此，目前已证明该模型实例在 32K 配置下能够处理并检索约 28K tokens 的简单合成文本。尚未证明复杂代码推理、长历史状态压缩或真实 Agent 工具循环在 28K 同样可靠；也没有测到 32K 临界点。

## 八、当前工程判断

| Vigil 中的职责 | 当前建议 |
|---|---|
| 任务规划与分析 | 进入隔离真实任务试点，需验收输出 |
| 工具参数生成 | 使用结构化输出与 Schema 校验，工具执行层仍须检查权限 |
| 代码修复辅助 | 可在临时项目试点，以真实测试结果验收 |
| 上下文摘要 | 仅作辅助；程序保存权威任务状态 |
| 自动部署、删除和高权限命令 | 暂不由本轮成绩授权 |

目前可以按需选择 16K 或 32K 上下文，不能再使用“32K 实际只能读 16K”的旧结论。

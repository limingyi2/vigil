## 结论

插件禁用后的失败不是 E2E 初始选错 Core target。E2E 选择的是 Core `file:///D:/vigil/client/src/index.html` 页面，禁用 API 返回成功，插件注册表和权限随后被同步撤销。关闭插件 BrowserWindow/WebContents 后，Core 的 CDP `Runtime.evaluate` 超时，调试端点也停止响应；测试安排的禁用后 Fake Provider 聊天请求没有到达 Fake Provider。关闭插件 renderer 是稳定触发点。

通过 `VIGIL_DIAG_NO_CLOSE=1` 保留插件窗口的控制实验中，Core `Runtime.evaluate('1 + 1')` 返回 2，浏览器级 `/json/list` 和 `/json/version` 正常。对 `BrowserWindow.close()` 改为 `BrowserWindow.destroy()`、实验性地共享插件 session，以及临时移除 `will-frame-navigate` 拦截，问题仍复现；帧导航拦截随后恢复。额外对照确认：空白插件 scheme 窗口使用相同 preload、session、安全导航监听，显示并保留 1.5 秒后关闭，Core 仍工作；实际插件窗口即使跳过业务 JS，关闭后仍复现。因此故障绑定于实际插件宿主创建/装载后的同 Electron 实例 teardown，不是插件业务 JS、普通子窗口关闭、初始 target 选择或权限撤销。Core BrowserWindow/WebContents 没有 close、closed、destroyed、render-process-gone、did-fail-load；但 Core 主进程心跳在 guest WebContents destroyed 后仅再输出一次，然后主循环停止，CDP websocket 无命令响应且浏览器调试 HTTP 端点停止响应。尚未取得 Electron 原生阻塞栈，无法断言具体原生调用；同实例窗口关闭方案没有可靠修复，应迁移插件 UI 到独立 Electron 子进程后再验收。

## 禁用时间线与观测

在 `%LOCALAPPDATA%\Temp\vigil-p5-joint-tfRIul\electron.log` 中，Core target 为 `90A6F141E4A44A47DD5C547C8F300400`，URL 为 `file:///D:/vigil/client/src/index.html`。禁用 API 在 2026-10-19 14:36:25.319（本地时间）返回 HTTP 200 / `ok:true`。同一时刻 Broker 顺序记录：

1. `/api/plugins/channels` 的 registry sync 从 `brain-vigil_smoke` 开始。
2. `permission revoke begin`，随后 `permission revoke end`，登记状态已删除。
3. `registry sync end []`，主进程记录 lifecycle refresh 返回 0 个 UI。
4. 插件 Window `close` 事件触发，`webContents` 被销毁；插件 Core PID 与 guest PID 分别为 15276 与 17620（同次基线诊断）。
5. 没有 Core `close`、`closed`、`destroyed`、`render-process-gone` 或 `did-fail-load` 事件记录，也没有捕获到主进程或 renderer 首个 JS 异常。
6. 同一 CDP websocket 仍处于 OPEN（readyState 1），但 Core `Runtime.evaluate` 超时；浏览器 `/json/version` 超时，`/json/list` 在 teardown 后也会超时。一次采样仍能列出原 Core target 和插件 target，所以连接起始 target 不是插件页面。
7. 主进程采样心跳在 guest teardown 后停止输出。测试自身最终在失败清理时结束 Electron 子进程（退出码 1）；这不是产品自然退出事件。

控制组保留 guest window 时，Core 页面仍可执行表达式，说明“单纯禁用 API / registry 清空 / 权限撤销”不会触发现象。切换为 `destroy()` 或共用 guest session 均未消除现象。Core 的禁用后 Fake Provider 聊天未通过；因此不能把该问题归类为只影响 CDP 的假失败。

## 2026-10-19 架构修复与复验补记

以上为同 Electron 实例故障的原始诊断结论。之后按其建议把通用插件 UI renderer、Chromium browser process 和窗口生命周期移到第二个 Electron 子进程。Core 通过随机令牌认证的 loopback TCP Broker channel 与宿主通信；插件 renderer 仍使用独立 preload、sandbox、context isolation、独立 session 和逐请求授权校验。宿主收到 `render-process-gone` 时通知 Core 回收整个插件 Electron 子进程；Core 继续响应，下一次打开会启动新宿主。

独立宿主实测后，目录插件 renderer 崩溃、宿主退出及重启、Core 聊天、插件禁用撤权/页面注销、禁用后 Fake Provider 新聊天、重新启用均通过。`node tools/test-electron-brain-e2e.js --quick-lifecycle` 连续串行 10/10 轮通过。综合 Electron E2E 最终 13 项通过；完整运行曾有 Fake Provider seed turn 中断，后续运行通过。Python 全套修复后 1371 passed，19 skipped，47 subtests passed。

这只解除禁用插件后的 Core 无响应问题，不代表整阶段交付完成。Wallpaper 的 UI 仍在隔离设置 renderer，尚无独立桌面背景窗口/Windows 桌面层级，GPU/WebGL 未验证；详见 [`P9.2B_ACCEPTANCE_REPORT.md`](P9.2B_ACCEPTANCE_REPORT.md)。因此目前仍不生成候选包、不推送、不合并。

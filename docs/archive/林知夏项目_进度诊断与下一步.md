## 三、核心问题：架构和你设想的不一样

你描述的方案是：

> API 生成内容 + 本地微调模型润色，让 API 的输出有真人感

但代码里的实际做法是：

```python
# pet.py / chat_memory_v2.py —— 本地模型直接生成全部回复
out = self.model.generate(ids, max_new_tokens=90, temperature=0.95, top_p=0.95)
```

API（config.json 里的 SiliconFlow DeepSeek-V4-Flash）**只被用在记忆提取**上：

```python
# memory_store_v2.py —— API 唯一的用处
MemoryStore.extract_with_api(user_text, api_config)
```

### 这个错位有什么后果

你的 LoRA 现在是"主生成器"，要同时负责语义理解、逻辑、共情、事实一致性。4B 模型扛不住最后一项，所以出现了这种**编造细节**：

| 你说 | 她回 | 问题 |
|---|---|---|
| 我今天写代码写得好累 | "让你老老实实**写作业**去！……明天**实习**记得多喝水" | 把"代码"听成"作业"，凭空冒出"实习" |
| 我今天被老师骂了 | "谁让你**当着全班同学说那些话**了" | 你没说过这话，她编的 |
| 在干嘛呢 | "刚下完**暴雨**，还带了**小鱼干**" | 凭空造景 |

**语气是对的，事实是错的。** 这正是"让小模型做主生成"的典型症状。

而你的原始设计恰好能治这个病：让大模型保证"说得对"，让你的 4B 只管"说得像她"。**你微调的方向是对的，只是接错了位置。**

## 七、后续改动：记忆库重构（2026-09-17 晚）

### 背景

原方案每条记忆存一个 `.npy`（`emb\*.npy`），检索时 `np.load()` N 次。查过磁盘后发现：D 盘是机械硬盘（ST3000NM0033），F 盘是 NVMe 固态（GXF-S-1TB-2280-PRO）。逐条随机小文件读取在机械盘上是灾难，但在固态上感觉不出来。

顺带确认：记忆库**极不占空间**，每条向量 2176 字节，1 万条也才约 22 MB。所以搬不搬家跟空间无关。最终决定**留在 F 盘**，但把性能问题一并修掉。

### 改了什么（`memory_store_v2.py` → v2.1）

1. **向量合并成单文件矩阵** —— `vectors.npy`（N×512 float32）+ `ids.json`（行序映射），替代 N 个散装文件
2. **索引首次加载后常驻内存** —— 检索变成纯矩阵运算（`Mn @ q`），之后零磁盘 IO
3. **自动迁移旧格式** —— 首次加载时检测到 `emb\*.npy` 会自动合并迁移，无需手工处理
4. **自动补算** —— memory.json 里手工加的条目若没有向量，会自动批量补算
5. **目录可配置** —— `config.json` 新增 `memory_dir` 字段，`get_default_store()` 统一入口
6. 新增 `stats()` 方法，一行看记忆库概况

配套改动：`pet.py`、`chat_memory_v2.py` 改用 `get_default_store()`；`demo_memory_v2.py` 原来会 `shutil.rmtree` 正式记忆目录，已改为使用临时目录。

### 实测（D 盘机械硬盘，800 条记忆）

| 项目 | 旧方案 | 新方案 |
|---|---|---|
| 写入 800 条 | 18.01 s | 2.66 s |
| 向量文件 | 800 个，共 1.66 MB | 1 个，1.56 MB |
| **单次检索** | **140.2 ms** | **1.4 ms** |
| 冷启动（新进程） | 1.03 s | 0.91 s |

单次检索快 **99 倍**。冷启动差异不大是因为耗时主要花在 Python 与嵌入模型加载上，不是读向量。

注意：上表的 140ms 还是**有系统缓存**的情况下。真正在机械盘冷读会更慢，所以这个改造在 F 盘上收益有限，但如果哪天真要搬到机械盘就是必须的。

- 现有记忆已清空（备份在 `F:\Unsloth\memory_backup_20260917_013435`）

## 八、对话引擎改造：两阶段 → API 直出（2026-09-17 夜）

### 期望与实测不符

按原计划实现了 `brain.py` 的两阶段生成（API 出草稿 → 本地 4B 按草稿重说），并在 800 条记忆的上下文下跑了 5 组对比。**结论是两阶段反而更差。**

例：问"我那只猫今天一直睡觉，会不会是生病了"

| 环节 | 输出 |
|---|---|
| API 草稿 | 笨蛋，猫本来就能睡啊，我家奶昔一天能睡十几个小时呢。不过你要不放心就摸摸它鼻头，湿湿的就没啥事。 |
| 两阶段（4B 改写后） | ……我养过一只猫，它一天睡十几个小时呢。……不过你放心，**我明天就去看一看** |
| 本地直出 | ……你说过你养的那只猫叫什么来着，布偶猫，是吧 |

草稿是对的（记住了奶昔、给了可操作的判断方法）。4B 改写后加进了"我养过一只猫"（猫是他的）和"我明天就去看一看"（设定上异地，她来不了）。

### 为什么两阶段会跑偏

LoRA 是用 `{system:人设, user:用户的话, assistant:她的回复}` 训的。把 API 草稿作为"意图"塞进 system，输入格式和训练时不一致，4B 会顺着自己的习惯生成，把草稿里的正确信息替换成它自己的臆测。

**要让本地模型真正胜任"改写"，必须用 `{草稿 → 知夏口吻版}` 格式的数据重训。** 这是后续可做的事（可用 API 自己造这批数据，属于蒸馏）。

### 采用的方案：API 直出

`brain.py` 提供三种模式，由 `config.json` 的 `chat_mode` 控制：

| 模式 | 说明 |
|---|---|
| `api`（默认，推荐） | API 直接产出她的话。实测最准最自然：事实对、会用记忆、有人设、不编造 |
| `two_stage` | API 出草稿 → 本地 4B 重说。目前会把草稿改坏，暂不推荐 |
| `local` | 纯本地 4B。离线兜底 |

API 不可用时前两种自动退回本地直出，不会崩。

**关键的一处 prompt 约束**（实测很有效）：

> 你们不在同一个城市。不要说"我马上过来""我明天去看""我陪你"这类话，也不要假装能看见他身边的东西（他的猫、他的宿舍）
> 不要随便用"又"字，除非他明确说过之前也这样
> 记忆只在自然的时候提，别每句话都硬塞

加上之后，"我马上过来"这类违反设定的输出消失了。

### 顺带修掉的两个 bug

1. **气泡从来没显示过。** 原来 `show_bubble` 用 QLabel 当子控件放在负 y 坐标，Qt 会把子控件裁剪到父窗口范围内，那段根本画不出来。改成独立的顶层 `Bubble` 窗口（`pet.py`）。
2. **`demo_memory_v2.py` 会 `shutil.rmtree` 正式记忆目录**，已改为临时目录。

### 现在的 pet.py

- API 模式下**不等 4B 加载完就能聊**（`ready` 提前置位），模型在后台慢慢加载，加载完自动接管兜底
- 聊天窗会显示 `[API直出]` / `[两阶段]` / `[本地直出]` 标签，方便排查走的哪条路

### 怎么用

### ⚠️ 隐私提醒（必须知道）

打开截屏模式后，**你的桌面内容会被上传到 SiliconFlow 的服务器**。这意味着：

- 密码输入框、私人聊天、浏览器历史都可能被拍进去
- 虽然截图不落盘、用完即删，但已经发出去了就没法撤回

所以：
- **默认是关的**（`config.json` 里 `watcher.use_screen: false`）
- 建议在输入密码、看私人信息时手动关掉，或干脆一直用轻量模式
- 轻量模式完全不截屏，零隐私风险，只是知道得粗一些

## 十五、本地视觉模型实测（2026-09-17 03:40）—— 结论跟预估相反

用户问：能不能用本地识图模型？性能损失大吗？

**下载了 Qwen2.5-VL-3B-Instruct（7GB）实测，结论推翻了我的预估——本地更快。**

### 实测数据（RX 9070 XT 16GB，4bit 量化）

| 指标 | 本地 3B (4bit) | 云端 8B API |
|---|---|---|
| 模型加载 | 17~37 秒（一次性） | 无 |
| 首次推理 | 3.3~14 秒（CUDA 预热） | — |
| **稳定推理** | **0.48 ~ 0.82 秒** | **4.3 秒** |
| 显存占用 | 2.49 GB 常驻 | 0 |
| 截图是否外传 | ❌ 不出本机 | ✅ 上传 |
| 输出正确性 | 简单问法下正确 | 正确 |

**稳定后本地比云端快约 5 倍。**

### 过程中的两个坑

1. **3B 模型输出 JSON 的能力很差** —— 实测输出成乱的（`{ ( and, detail详细描述...`）。
   改成"两行纯文本 + 按行解析"后稳定。这是小模型做结构化输出时的通病。

2. **模型会照抄提示词里的"第一行/第二行"** —— 输出变成`第一行：他正在使用...`。
   解析时加了正则清洗。

3. **首次推理要 3~14 秒** —— 是 CUDA kernel 预热，不是模型慢。
   解决办法：开本地模式时后台预热一次，之后就是 0.5 秒。

### 对打游戏的影响（关键）

| 场景 | 影响 |
|---|---|
| 打游戏时 | **零影响** —— 检测到游戏进程会 `unload()` 把 2.49GB 显存还给游戏 |
| 平时常驻 | 占 2.49GB 显存。16GB 卡上，游戏要 8~12GB，塞得下但会让游戏可用显存变紧 |
| 每次分析 | GPU 满载 0.5~0.8 秒，3 分钟才一次，基本无感 |

**默认仍是云端**（`use_local_vl: false`），因为本地要常驻显存。想要隐私就手动切。

### 怎么切

右键 → 「用本地模型看（截图不出本机）」。开了会自动后台预热（约 20 秒），之后每次 0.8 秒。

| `vlm_local.py` | 本地视觉模型封装，含 `load/unload/describe` |

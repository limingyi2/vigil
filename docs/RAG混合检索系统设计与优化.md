# RAG 混合检索系统设计与优化

> 桌面 AI Agent 项目 Vigil（产品名 Kestrel）的知识库检索子系统，从 0 到 1 搭建混合检索管道，并完成三阶段性能优化。

## 一、项目背景

桌面 AI Agent 需要在本地管理大量知识（聊天记录、记忆、文档、代码），传统的关键词检索无法理解语义，纯向量检索在精确匹配场景下表现不佳。本项目设计并实现了一套 **BM25 + 向量 + RRF 融合** 的混合检索系统，支持亿级向量规模的 ANN 索引，并针对桌面场景做了轻量化优化。

## 二、系统架构

```
用户提问
   ↓
┌─────────────────────────────────────────┐
│           unified.retrieve()            │
│  统一检索入口（scope 过滤 + 降级链）      │
└──────────┬──────────────────────────────┘
           │
     ┌─────┴─────┐
     ▼           ▼
┌────────┐  ┌────────┐
│  BM25  │  │  向量  │
│ (FTS5) │  │ (ANN)  │
└───┬────┘  └───┬────┘
    │           │
    └─────┬─────┘
          ▼
   ┌──────────────┐
   │ RRF 融合排序  │
   │ (K=60)       │
   └──────┬───────┘
          ▼
     检索结果
```

### 核心组件

| 组件 | 技术选型 | 说明 |
|---|---|---|
| 关键词检索 | SQLite FTS5 | 零配置，内置 BM25 排序，适合桌面应用 |
| 向量检索 | FAISS HNSW | 近似最近邻，M=16, efSearch=50，支持增量更新 |
| 融合算法 | Reciprocal Rank Fusion (RRF) | 无参数融合，K=60，结合两路排序优势 |
| 嵌入模型 | bge-small-zh-v1.5 | 512维，约100MB，CPU可跑，中文语义理解优秀 |
| 存储 | SQLite + 扁平文件 | 主库35张表，向量独立存储，FAISS索引持久化 |

### 数据模型

- **search_docs**：文档正本（id, scope_kind, title, body, source, owner, src, persona, chan, meta）
- **embeddings**：向量存储（doc_id, model, dim, vector BLOB, created_at）
- **scope_kind**：6种分区（chat/memory/kb/workspace/plugin/other），支持按类型过滤

## 三、三阶段优化

### Phase 1：能力注册中心接入

**问题**：检索和知识库功能分散在各模块，Agent 无法自动发现和调用。

**方案**：实现统一能力注册中心，Agent 通过 `capability_status` / `capability_call` 两个工具自动发现和调用所有能力。

**新增能力**：

| 能力 | 操作 | 说明 |
|---|---|---|
| unified_search | status/search/sync/reindex | 混合检索，覆盖全部分区 |
| knowledge_base | status/list/search/ingest_text/ingest_path/delete/reindex | 知识库投喂与管理 |

**效果**：用户说"帮我搜知识库"，Agent 自动识别并调用 `knowledge_base.search`，无需手动操作。后续新增功能只需注册即可被 Agent 发现。

### Phase 2：知识库统一向量化存储

**问题**：知识库模块有自己独立的向量化实现（kb/embedder.py + vectors.npy），和统一检索的 embeddings 表是两套系统，互不互通，数据重复存储。

**方案**：

1. **投喂时自动同步**：kb.ingest_text 成功后，自动将文本块写入 search_docs，并调用统一嵌入后端建向量到 embeddings 表
2. **检索优先走统一通道**：kb.search 优先调用 unified.retrieve(kinds=['kb'])，失败降级到旧的 npy 暴力扫描
3. **删除同步**：delete_doc / clear 同步删除统一检索中的对应文档
4. **配置开关**：新增 `use_unified_search`、`sync_to_unified` 两个配置项，可独立控制

**修复的 Bug**：chunker 返回的 chunks 缺少 source 字段，导致 doc_id 中 source 为空，删除时 pattern 不匹配。修复为在同步前补全 source 字段。

**测试验证**：

```
投喂测试文档 → search_docs 1条 + embeddings 1条 ✅
kb.search "向量检索融合" → 返回1条，score=0.033 ✅
delete_doc 清理 → 统一检索 kb 文档数=0 ✅
```

### Phase 3：轻量化优化

**问题**：桌面场景内存敏感，向量化模型常驻占200MB，重复查询浪费算力，FAISS 索引每次查询从数据库全量读取。

#### 3.1 查询向量缓存

**实现**：全局字典缓存查询向量，key=query 的 MD5，TTL 1小时，上限1000条，超限时 LRU 式清理最旧的一半。

**真实测试数据**：

| 查询次数 | 耗时 | 说明 |
|---|---|---|
| 第一次 | 135.5ms | 未命中缓存，调用嵌入模型 |
| 第二次（相同query） | **0.9ms** | 命中缓存，跳过模型调用 |

**加速比**：**150倍**。对于用户反复追问同一话题的场景，效果显著。

#### 3.2 模型空闲卸载

**实现**：EmbeddingBackend 记录 `_last_used` 时间戳，每次 embed 成功后更新。下次调用时检查空闲时间，超过 `IDLE_UNLOAD_SECONDS`（默认300秒=5分钟）自动卸载模型，释放内存。下次查询重新加载约1-2秒。

**内存收益**：模型卸载后释放约 **200MB** 内存。桌面用户长时间不提问时，客户端内存占用显著降低。

#### 3.3 ANN 索引增量更新

**实现**：index_embeddings 写入数据库后，如果 FAISS 索引已加载，自动调用 `ann.add()` 增量添加新向量并持久化。避免下次查询时全量重建索引。

**FAISS HNSW 参数**：
- M=16（每层最大连接数）
- efSearch=50（搜索时访问的候选数）
- 墓碑删除 + 20%阈值触发重建
- 索引持久化到 `embeddings_hnsw.faiss` + `embeddings_hnsw.meta.json`

## 四、性能对比

### 嵌入后端对比

| 后端 | 模型 | 500条索引耗时 | 查询耗时 | 说明 |
|---|---|---|---|---|
| 云端 API | bge-m3 (硅基流动) | 11.4s | 300-400ms | 依赖网络，延迟高 |
| 本地 CPU | bge-small-zh-v1.5 | 5.0s | 85-89ms | 离线可用，快约4倍 |

### 数据规模对比

| 数据量 | 暴力扫描查询 | ANN 索引查询 | 缓存命中查询 |
|---|---|---|---|
| 500条 | 85ms | - | 0.9ms |
| 1万条 | 330ms | ~100ms（预估） | 0.9ms |

### 内存占用

| 状态 | 内存占用 |
|---|---|
| 模型加载中 | ~200MB（模型权重）+ 索引内存 |
| 模型空闲卸载 | ~20MB（仅索引元数据） |

## 五、技术亮点

1. **混合检索三通道**：BM25（精确匹配）+ 向量（语义匹配）+ RRF（无参数融合），兼顾精确性和语义理解
2. **本地优先架构**：嵌入模型本地运行，数据不出端，隐私安全，离线可用
3. **懒加载 + 空闲卸载**：模型和索引按需加载，5分钟无操作自动释放，桌面场景内存友好
4. **查询级缓存**：相同 query 命中缓存后查询耗时从 135ms 降到 0.9ms
5. **能力注册中心**：所有功能统一注册，Agent 自动发现和调用，新增功能零成本接入
6. **多分区隔离**：聊天/记忆/知识库/工作区/插件 6种分区，支持按类型过滤和权限控制
7. **完整降级链**：向量检索失败自动降级纯 BM25，统一检索失败降级知识库旧实现，确保可用性

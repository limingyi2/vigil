# Python 插件

可选插件通过明确安装流程写入 Brain 数据根目录的 `data/installed_plugins/`。仓库中的 `brain/plugins/` 是源码与兼容参考；将文件放在该目录不会自动安装，也不会使它进入正式安装包。

## 开发入口

最小模板位于 [templates/plugin-basic](../../templates/plugin-basic/README.md)。从模板开始，可以先验证目录结构，再生成安装清单或通过 Creator 的草稿安装流程安装。

```powershell
python tools/check_plugin_structure.py templates/plugin-basic
```

检查器只读取结构和元数据，不导入、不安装或执行插件。静态检查通过不代表运行行为已验证。

## 工具与钩子

| 声明 | 用途 |
| --- | --- |
| `NAME`、`DESC` | 插件标识与说明 |
| `TOOLS` | 工具名到执行函数的映射 |
| `TOOL_SPECS` | 模型可见的描述、参数和调用约定 |
| `FEATURE` | 可选的功能开关标识 |
| `prompt(ctx)` | 可选的上下文补充 |
| `on_turn_in(ctx)` | 可选的输入阶段钩子 |
| `on_reply(ctx, text)` | 可选的回复阶段钩子 |

`TOOLS` 和 `TOOL_SPECS` 需要保持一致。只提供执行函数而没有工具规格，不能保证模型能够发现或调用该工具。描述中应写明操作、参数和限制，不把所有场景都写成强制调用规则。

插件的参数形式以工具规格和宿主调用实现为准；多参数工具需要遵守宿主的字典参数约定。新增工具后要检查清单暴露与实际分发两条路径。

## 打包与安装

当前安装路径区分 Creator 的扁平插件包和市场的带清单制品，不能将两者混用。Creator 模板的结构要求见模板 README；市场插件按 `manifest.json`、协议与文件哈希校验。

带前端资源的插件还需要通过客户端资源和窗口加载规则。前端代码获得安装批准后由客户端执行；结构检查和哈希核对不是代码行为沙箱。

市场安装从条目获取制品；按链接安装先解析清单并执行来源、权限与完整性检查。安装、加载、启用和实际调用是不同状态，界面应展示真实回执。

## 生命周期与数据

插件管理由 `plugin_manager.py` 处理，文件事务由 `plugin_ops.py` 处理，运行时加载由 `plugin_host.py` 处理。新增安装入口应复用已有事务，避免另写一套启停与卸载逻辑。

调用前需要确认所属插件已经加载并启用。卸载后不能继续暴露遗留工具规格，后续重装或升级也不能绕过用户已卸载的状态。插件自己的持久化数据应使用宿主提供的受控目录，并明确卸载时的处理策略。

核心适配器与可选插件使用不同分发边界。市场、Skill Host 等核心基础设施不能通过把整个可选插件目录打包进 Brain 来获得。

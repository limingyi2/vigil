# 知夏的推理架构升级：ReAct / Plan-and-Execute / 思维链

> 2026-10-04 拟。基于现有代码实测状态写的，不是通用教程。
> 每条都指明**改哪个文件**、**为什么**、**怎么验收**。

---

## 零、先看清楚我们已经有什么（别重复造）

`brain/tools.py:137 run_chat_with_tools()` 现在的循环：

```
她写 [tool:weather:杭州]
   ↓
执行工具，结果拼成「系统提示」塞回对话
   ↓
再问她一轮（最多 4 轮）
   ↓
清扫残留标签 → 返回给用户
```

**这本身就是 ReAct 的第 1、2 步**（Thought→Action→Observation），只是没有显式的
"Thought" —— 她把"我想调用天气"和最终答案混在同一段文字里输出。

所以这次不是"从零加 ReAct"，是三件事：

| 能力 | 现状 | 要补的 |
|---|---|---|
| ReAct | 有循环，无显式推理 | 把 Thought 显式化、可观测、但不进群 |
| Plan-and-Execute | **完全没有** | 多步任务的规划层 |
| 思维链 | 隐式（藏在最终答案里） | 独立存储、可回放、跨轮记忆 |

---

## 一、ReAct：把"想什么"和"说什么"拆开

### 为什么要拆

现在她一次输出同时承担两件事：
1. 生成 `[tool:x]` 标签（机器读）
2. 生成给用户看的话（人读）

问题有三个，都实测过：

- **推理泄漏**：她想的过程会跟着回复一起发到群里（群聊致命）
- **无法观测**：`trace.tool` 对内置工具常为空，事后看不出她为什么没调
- **无法干预**：她一旦写错，脏话已经在上下文里了

### 改法：双输出 + 私有通道

`brain/tools.py` 里加一个轻量解析层，不动模型调用方式：

```python
REACT_RE = re.compile(
    r"<think>(?P<think>.*?)</think>\s*"
    r"(?P<act>(?:\[tool:[^\]]+\]\s*)+)"
    r"(?P<rest>.*)",
    re.S)

def parse_react(raw):
    """把一轮输出拆成 (思考, 动作, 回答)。

    没有 think 标签时全部算 rest —— 老行为不变，
    不因为格式没出来就让她哑掉。
    """
    m = REACT_RE.search(raw or "")
    if not m:
        return "", [], (raw or "").strip()
    return (m.group("think").strip(),
            re.findall(r"\[tool:([^\]]+)\]", m.group("act")),
            m.group("rest").strip())
```

**关键：思考部分只进 trace，永不进回复、永不进群。**

### 提示词侧（`brain/persona_store.py` 的工具段）

```
要查东西时，按这个格式写（只你自己看到，用户看不到）：

<think>我要查杭州天气，不用问他在哪，他刚说了在杭州</think>
[tool:weather:杭州]

然后正常回答他。想的过程别混进回答里。
```

**注意别给"场景映射"** —— 只说格式，不说"什么问题该用什么工具"。
那些映射她自己看 `TOOL_HELP` 里的可选项自己挑（这是已经踩过的坑）。

### 验收

拿一道**她不可能凭记忆答对**的问题：北京今天几度 / 23.5×4.7 /
某个小版本号。看两个数：
- `trace.think` 非空（说明推理被记下来了）
- 最终回复里**没有**任何推理痕迹（`意图：`、`首先`、`我需要`）

## 二、Plan-and-Execute：多步任务的规划层

### 为什么不能只靠 ReAct

ReAct 是"想到哪做到哪"。遇到这类任务它会崩：

- "帮我把这周的会议纪要整理成周报发给我"（要查日历 → 读文件 → 汇总 → 发送）
- "找出我上周说的那个链接，再告诉我是什么东西"（多轮检索 + 交叉判断）

ReAct 会在第一步就急着回答，或者在第三步忘了第一步查到了什么。

### 加什么

新插件 `brain/plugins/plan.py`，复用现有钩子，**核心零改动**：

```
用户消息
  ↓
on_turn_in
  ↓
planner 模型（便宜 flash 级）判断：这需要规划吗？
  ├─ 不需要 → 什么都不做，走原来的 ReAct 路径
  └─ 需要 → 生成 plan.json
       ↓
     Brain 按计划逐步执行
       ↓
     每步结果回写进上下文
       ↓
     on_reply 组装最终答案
```

### plan.json 的形状（最小版，别做复杂）

```json
{
  "goal": "整理本周会议纪要成周报",
  "steps": [
    {"n": 1, "intent": "找出本周所有会议的纪要",
     "tool": "files", "arg": "会议纪要 本周", "why": "没有纪要就没法汇总"},
    {"n": 2, "intent": "汇总成周报格式",
     "tool": null, "arg": null, "why": "把多份合成一份，需要她自己写"}
  ],
  "fallback": "任何一步失败就把已拿到的部分给用户，说明哪步没成功"
}
```

### 三个必须防的坑

**① 规划太贵 / 太多余**

不是每句话都要规划。判定标准要有，但**给判据不给场景映射**：

```
需要规划：这件事要三步以上才能做完，或者做一半发现做不完
不需要：一问一答能答的、只是要查个东西
拿不准：不需要（默认走原路径，别浪费钱）
```

**② 步骤卡死**

必须有步数上限（建议 5 步）和**每步必须有 fallback**。
规划模型也会写出"第 3 步：等用户回复"这种死步骤 —— 判定层要拦。

**③ 半途而废比答错更糟**

`fallback` 字段是必须的：任何一步失败，**把已经拿到的结果给用户**，
附一句"第 N 步没成功"。最糟的是她默默卡住不说话。

### planner 用哪个模型

同一个判断：planner 不需要聪明，需要**便宜、快、格式稳**。
用和 `gate.py` 同一个模型（`DeepSeek-V4-Flash`，实测 1.8 秒/条）。

复用 gate 的实测结论：**别掐 max_tokens**，给 200 让它写完。

### 什么时候开

**默认关**。和 gate 一样的逻辑 —— 新链路没在真实场景验过之前不要挂上去。
建议顺序：先在 App（`src=app`）上试，那里你能直接看到全流程。

## 三、思维链：独立、可回放、能跨轮

### 和 ReAct 的区别

ReAct 的 think 是**这一轮**的。思维链要做的是**留痕**：

- 这一轮她想了什么 → 落盘
- 上一轮她为什么那么答 → 能查
- 反复出现的推理模式 → 能统计（比如"她总在天气问题上绕过工具"）

### 落盘设计

`brain/data/react/YYYY-MM-DD.jsonl`：

```json
{"ts": 1785000000, "src": "app", "turn_id": "...",
 "user": "北京今天几度",
 "think": "他问温度，得查实时数据，不能凭记忆",
 "tools": [{"name":"weather","arg":"北京","ok":true,"ms":820}],
 "reply": "北京现在 3 度",
 "elapsed_ms": 4210, "rounds": 2}
```

**绝对不放**：完整 prompt、API key、记忆库内容。
思维链涉及她的内部状态，导出前要过滤。

### 接口

- `GET /api/react/recent?limit=20` —— 最近几轮的思考与工具
- `POST /api/plugins/... ` 里挂一个导出按钮（可选）

### 这才是"可观测"的价值

之前你查"她为什么不调工具"，只能靠猜 + 翻日志。有了思维链：

- `tools: []` → 她压根没想调（提示词问题）
- `tools` 有但 `ok: false` → 工具坏了（工程问题）
- `think` 显示她判断错了 → 判据问题

**三种病因三种治法，没有 trace 全靠猜。**

---

## 四、落地顺序（重要）

**不要三个一起上。** 一起来出问题分不清是谁的锅。

| 阶段 | 做什么 | 验收判据 | 风险 |
|---|---|---|---|
| 1 | ReAct 显式化（解析 + 提示词 + trace） | 3 道实时题，答案对且**回复里没有推理痕迹** | 低。格式没出来会回落老行为 |
| 2 | 思维链落盘 + 接口 | 能查到最近 20 轮，字段齐 | 极低。只加文件 |
| 3 | Plan-and-Execute（默认关） | 一个真多步任务能跑完 3 步以上 | **中**。卡死/半途而废 |
| 4 | 在群里开 | `@麦麦` 能回、能沉默 | 已有闸门兜底 |

**每阶段都独立可回滚**：关一个 config 键就退回上一步。

## 五、跟你现有架构的关系（这条最重要）

知夏已经是插件化架构，所以这三样**都做成插件**：

- `brain/plugins/react.py` —— 解析 + trace（钩子 `on_reply`）
- `brain/plugins/plan.py` —— 规划（钩子 `on_turn_in`）
- 思维链写入可以并进 react.py，不必单独一个

**`server.py`、`tools.py` 核心一行不用改。**

这正是当初插件系统设计的回报 —— 7 处核心改动之后，
之后每个新功能都只是"丢一个文件进去"。

## 六、什么该做，什么别做

### 明确别做的

- ❌ **不要把思维链塞进上下文喂回给模型**（"你上次想的是…"）
  会污染人设、token 爆炸、她开始演自己的思维过程
- ❌ **不要规划每个对话**。planner 每次调用都是钱和时间
- ❌ **不要给场景映射**（"问天气就调 weather"）—— 已经踩过，
  正向白名单漏一项她就静默不调

### 一定要做的

- ✅ 每层都独立可关（`config.json` 一个键）
- ✅ 每层都有降级（格式没解析出来 → 老行为；planner 崩 → 走 ReAct）
- ✅ 验收用**实时问题**，不用"她能不能记住我的生日"这种
- ✅ trace 落盘在**云端**，不在本机（本机只是壳）

## 七、成本估算

以硅基 DeepSeek-V4-Flash 实测单价为基准（1.8 秒/条）：

| 层 | 调用时机 | 单次 token | 日均（假设 50 轮）|
|---|---|---|---|
| ReAct 解析 | 0（纯本地正则） | **0** | **0** |
| 思维链落盘 | 0（本地写文件） | **0** | **0** |
| Plan-and-Execute | 只在判为"需要规划"时 | ~600 | 假设 10% → 5 次 |

**ReAct 显式化和思维链落盘是零成本的** —— 纯本地改动。
只有 Plan-and-Execute 要花钱，而且只在真需要规划时才花。

这一条很重要：先把零成本的两层做掉，验证有效再上花钱的那层。

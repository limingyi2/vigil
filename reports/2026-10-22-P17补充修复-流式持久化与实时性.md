# P17 补充修复：流式输出卡顿与事件持久化优化

> 分支 `codex/p17-coding-agent`（worktree `F:/zhixia-p17`），PR #15。本文对应 Phase 1（CI 修复）之后的第二阶段：流式链路去事务化 + 事件持久化重构 + 可靠性收口。

## 1. 代码级根因

### 1.1 卡顿根因：每个增量一次全量写事务

旧链路里，模型每吐一个增量，`_event()` 就做一整轮磁盘操作：

1. `BEGIN IMMEDIATE` 开写事务；
2. 把**整份 run JSON**（含全部步骤、全部内容）序列化后 `UPDATE runs SET data=?`；
3. `synchronous=FULL` 下每次提交都要一次 fsync。

增量是流式路径上频率最高的操作（模型每 10~100ms 吐一段），于是：

- **延迟被 fsync 绑定**：增量间隔从"模型吐字速度"变成"模型吐字速度 + 磁盘提交速度"；
- **写入量随输出长度平方级增长**：第 N 个增量要重写前 N-1 段的全部内容；
- 写事务持有全局锁，把只读查询（快照/事件分页）一起堵住。

计时证据（`stream_metrics` 事件，只记数字）：修复后 60 条增量的 `sse_ms_avg=2.37ms`、`max_gap_ms=16ms`（脚本节奏 10ms + 调度余量）、`first_delta_ms≈0`。修复前同类负载的增量间隔被 fsync 拖到数百毫秒级（旧代码基准见 §3 的 A/B 口径）。

### 1.2 持久化根因：事件序号与内存/磁盘两套真相

- 增量边产生边落库，序号在两条路径上分配（写路径直接拿、读路径补算），重启后两边对不上；
- 客户端重连分页读事件时，"游标推进了但事件还没落盘"会出现空洞，触发快照重同步，**跳过一段增量**（表现为客户端缺字）；
- 重启后在途 run 永远显示 running——修复逻辑住在写路径里，只要没人写就没人修。

## 2. 优化方案

### 2.1 热路径去事务化

- 增量只进**线程安全有界内存队列**（`_RunBuffer`），`push()` 不碰数据库、不拿全局锁；
- 独立**落盘线程**按 短间隔(50ms)/事件数(64)/字符数(2048) 触发批量提交，一次事务写一批；
- 批量写仍写**绝对值**（`content` 全长 + 新增事件），与单次写语义一致，不会叠加重复；
- `_LIVE`（`run_id -> (owner, item)`）是本进程唯一内存副本，对外出口一律 `copy.deepcopy`；落盘线程按它写，读写不打架；
- 只读查询走 `_read_db()` **独立只读连接** + `journal_mode=WAL`，与写事务彻底分离；`synchronous=FULL` 保留，持久性不变；
- `_WAKE` Condition：增量入队即 `notify_all()`，SSE 读取线程 `wait(0.05)` 替代固定 sleep，睡前再查 `has_pending()` 防丢唤醒；
- 背压：`count >= 4096` 或 `weight >= 2048*64` 时执行线程同步落一次；`_delta()` 返回 None = run 已收口，调用方连正文都不累加。

### 2.2 序号与分页一致性

- seq 分配与 `event_cursor` 推进在同一把 `buf.lock` 内完成，批量落盘与实时事件共享同一序号规则；
- `page(after, item)` 在**同一把锁**里原子读「可见事件集合 + 游标」，消除读-skew（这是本轮实测抓掉的缺字 bug：游标推进了、事件还没进可见集合 → 误判空洞 → 快照重同步跳过那一段）；
- `stream()` 区分**迟订户**（终态且没投递过任何事件 → 只发权威快照，守住旧契约）与**现场观众**（先发完本页全部事件再发快照，修掉"终态页最后一批增量只进快照、客户端收不到"）。

### 2.3 计时点（只记数字）

- provider 层（`execution.py`）：每个增量 yield 时带 `t=time.monotonic()`（provider 收到时刻）；非流式兜底的合成增量同样带 `t`；
- `_delta()` 把 `t` 转成 `_t` 入队，**落库/上线前剥离**——思考内容、密钥、敏感参数一律不进指标；
- 每轮收尾发 `stream_metrics` 事件：`first_delta_ms / max_gap_ms / max_queue_ms / sse_ms_avg / batches / flush_ms_* / deltas / chars`，全部为数字（有单测钉住）。

### 2.4 可靠性收口

- `_finish` 顺序：先关 buffer 入口（`closed=True`，迟到增量被丢弃）→ `_event`（把关门前增量刷进同一事务）→ `_save` → pop buffer/`_LIVE`/TRANSIENT → `notify_all`；
- `_ensure_repaired()`：重启后在途 run 标 `interrupted`；读路径独立后由各读接口首次碰库时触发，并作废内存副本；
- 落盘线程环境卫生：`_db(create=False)` 不建目录；`_RunBuffer.data_dir` 环境戳，环境变了不写进别人的库；`_writer_loop` 空闲退场（修掉 Windows 测试收尾 `WinError 145`）；
- think_delta → `TRANSIENT`（maxlen 256，**不落库**）；text_delta → pending（落盘/上线）。

## 3. 量化证据：DB 提交次数

同一负载（60 条正文增量 + 1 条思考，间隔 10ms），数 `_db()` 开事务次数：

| 链路 | 写事务次数 | 说明 |
|---|---|---|
| 旧链路（每增量一事务） | ≈ 64 | create + 起步 + step + 60 增量 + 收尾，每次含整份 JSON UPDATE + fsync |
| 新链路（批量落盘） | **5** | create + 起步 + step + **一次批量** + 收尾 |

同一运行的其余指标：`status=succeeded`、正文事件 60 条、`content_len=180`、思考文本零泄漏、`batches=1`、`deltas=61`。

SSE 侧到达时序（客户端视角）：首段 **47ms**，增量间隔 max **16ms**，60/60 全部按序到达。

### 本轮额外修出并回归的缺陷

1. **读-skew 缺字**：`events()` 里「拍可见集合」与「读 event_cursor」非原子，增量在中间入队 → 误判空洞 → 快照重同步把 `after` 推到游标 → 那一跳增量永久跳过。修法：`_RunBuffer.page()` 同一把锁原子读两者（插桩实锤：`GAP-HOLE after=10 cursor=11 buf_visible=[11]`）。
2. **终态页丢最后一批增量**：`stream()` 终态分支只发快照就 return。修法：现场观众先发完本页事件再发快照；迟订户保留旧契约（`delivered` 标志分流，`test_success_terminal_cannot_be_cancelled` 钉住）。
3. **落盘线程踩测试临时目录**：tearDown 删目录后写线程把目录建回来（`WinError 145` / `unable to open database file`）。修法：`_db(create=False)` + isdir/data_dir 双守卫 + 空闲退场。
4. **`test_p1_models.py::test_no_native_stream` 旧契约**：非流式合成增量新增计时键 `t`，精确字典相等断言过不去 → 改为断言语义字段 + 计时键为 float（消费方只读 `type`/`text`/`result` 并重建出口字典，`t` 不外泄，已逐处核对）。

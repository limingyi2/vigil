### P0-2 Tool Call ID 一致性（任务书点名的真 bug）

**根因**：`brain/agent_runs.py` 旧 1301-1303 行。`_calls()` 清洗后的标识只用在
tool 消息（`tool_call_id=call[0]`）和台账（`call_id=cid`）；回写模型上下文的
`assistant_history_message(..., tool_calls=completion['tool_calls'])` 用的却是
**网关原始值**。三种情况下两边对不上：

- 网关没给 id → `_call_id` 生成 `call_0_xxxx`，回写侧根本没有 id 字段；
- 同批两个调用同一个 id → 清洗侧第二个加 `_1` 后缀，回写侧两个都还是原值；
- id 超 128 字符 → 清洗侧截断，回写侧全长。

严格网关（OpenAI 兼容及多数国内网关）在收到「tool 消息的 tool_call_id 不在前一条
assistant.tool_calls 里」时**直接 400 拒掉整个请求** —— 第一轮执行工具、第二轮
必死，多轮工具链断在这里。

**修复**：回写统一用清洗后的最终标识重建 tool_calls（`replay_calls`）。

**证据**：`test_p161_tool_consistency.py` 的 `StrictProvider` 在每次请求前校验
整个 transcript（tool 消息必须挂到前一条 assistant 的某个 tool_calls id 上）。
反向验证：回退该修复后 `test_missing_call_id_round_trips_through_the_whole_transcript`
与 `test_duplicate_ids_in_one_batch_are_disambiguated_everywhere` **失败**（run 以
invalid_structure 告终）；修复后通过，且断言 `assistant.tool_calls[].id ==
tool.tool_call_id == 台账 call_id` 三处一致。

### P0-4 错误诊断完整透传（台账 → SSE → Electron）

**根因**：`server.py` 的 `_agent_chat_events` 终态 error 事件只发
`class/msg/status`，**不带 `detail`**。非法工具调用根本没进入工具执行阶段，
前端没有步骤行可看，用户只看到一句「工具名称、参数或调用标识无效」——
不知道是哪个工具、哪个参数、哪种错误。

**修复**：
1. 终态 error 事件补发 `detail`（过 `_redact_error_text`）；
2. `_error()` 的 detail 落台账前统一脱敏（旧代码 `str(detail)[:200]` 原样入库）；
3. `last_invalid.detail`、`model_step.error.detail`、`invalid_calls` 全部过脱敏
   （`invalid_calls` 是本次新发现的泄漏点：它原样存模型发来的 function JSON，
   参数值可能就是钥匙）；
4. 前端 `pages.js` 的 error 分支与 `reconcileRun` 展开 detail；`remember()` 的
   error 记录也带上 detail。

**证据**：`test_invalid_tool_terminal_error_carries_a_redacted_detail` 断言终态
`error.detail` 含工具名 `write_note`、含 `sk-live-…` 被 `[已隐藏]`，且整个 item
JSON 里搜不到钥匙；`test_receipts_in_the_ledger_are_redacted` 覆盖收据路径。

### P0-5 执行状态统一（七态）

**根因**：`result_state` 按 reason **标签**推导：
`'not_dispatched' if reason == 'tool_failed' else 'returned'`。而 `tool_failed`
一个标签下至少有四种真相（客户端没认领 / 策略拦下 / 他点了拒绝 / 命令跑了退出码
非零）。**写文件、执行命令这类已派发、已失败的操作被记成"从未派发"** —— 续跑或
重试时去重表看到的是"没执行过"，副作用会再来一遍。

**修复**：新增 `_execution_state(reason, receipts, raised)`，只凭回执推导：

```
raised=True(适配器抛异常)          → unknown   （副作用是否落地无法证明）
reason=None / empty_output          → returned
reason=tool_unknown                 → unknown
回执含 unknown                     → unknown   （认领过但结果不明）
回执含 failed                      → failed    （确实执行了，且失败了）
回执含 denied                      → denied
其余                               → not_dispatched
```

同时修掉 `empty_output` 被笼统吞成 `tool_unknown` 的问题（收据已经说明"执行了、
只是没有输出"）。

**证据**：`_execution_state` 九组参数化 + 三个端到端（failed / denied /
empty_output）。反向验证：回退后 `test_write_that_ran_and_failed_is_marked_failed`
（断言 failed，实际 not_dispatched）与 denied 用例失败。

### P0-5b 迟到结果不翻旧 run 终态

**根因**：`_tool()` 收尾块无条件 `if reason: _finish(db, item, 'failed', reason)`。
插话/暂停/取消后旧 run 已是 stopped，在途工具的回执晚到，会把 `paused` 的旧 run
翻成 `failed` —— 「暂停可续」语义被破坏，前端看到旧任务失败而非暂停。

**修复**：只有 `item['status'] == 'running'` 才 `_finish`；否则只落 step。
（代码注释里本来就这么写，只是没实现。）

**证据**：`test_late_tool_result_never_flips_a_paused_run`：工具执行途中插话 →
放行在途工具返回失败回执 → 旧 run 保持 `paused`、step `result_state='failed'`、
子 run 正常 succeeded。反向验证：回退后该用例失败（旧 run 变 failed）。

### P0-6 完整脱敏

统一走 `_redact_error_text`（sk-/rk-/pk-/ghp-/xox-/AKIA/LTAI 前缀、Bearer、
全大写下划线环境变量名、32+ 位 hex；截断 400 字）+ `_safe_event_value`
（`api_key=` 形态、环境变量真值）。本次补齐的漏点：

| 漏点 | 旧行为 | 现在 |
|---|---|---|
| `_finish` 的 detail | 原样入库/进 SSE | `_error()` 内脱敏 |
| `last_invalid.detail` | 原样 | 脱敏 |
| `model_step.error.detail` | 原样 | 脱敏 |
| `invalid_calls` | 原样存模型 function JSON | 脱敏 |
| `step['receipts']` | **整个收据列表原样进台账+快照 SSE**（命令输出带回显密钥是现实场景） | 逐条脱敏 |
| SSE 终态 error 事件 | 无 detail | detail 脱敏后下发 |

保留工具名、字段名、错误类型（脱敏只替换值）。

### P0-7 图片识别剩余问题

1. **原始格式 vs 保存扩展名**：`_save_turn_image` 与 `ask_with_retry` 两处落盘
   **硬编码 `.jpg`**，PNG/WebP 截图被盖成 JPEG。新增 `_image_ext()` 按魔数嗅探
   （PNG/WebP/GIF/BMP/JPEG，RIFF 再核验 WEBP 四字标识），两处共用。
   **证据**：`test_p161_image_workspace.py` 三个归档测试走真实 HTTP handler，
   断言 PNG→.png、WebP→.webp、JPEG→.jpg。
2. **缓存跨权限边界**：`_IMAGE_DESC_CACHE` 原来只按内容哈希键。描述文本本身
   不含跨边界数据，但「这张图被分析过」这个事实不该跨身份/会话可见。缓存键加
   `scope`（调用方 owner，含身份+渠道+会话）。
   **证据**：`test_same_image_in_another_scope_is_analysed_again`：同图不同 scope
   → 视觉被调两次；同 scope → 复用。
3. 视觉不可用明说、同图复用、带图进 Agent run、描述不进存档 —— P16 已覆盖
   （`test_p16_stream_image.py` 全组通过），本次回归无破坏。

### P1-8 工作区路径真正绑定工具执行

**根因（剩余部分）**：P16 的 `test_p16_workspace_retrieval.py` 只证明了「显式传
roots 时客户端护栏有效」；「在 Vigil 界面选 `F:\zhixia` 后 Agent 真的在该目录
工作」这条端到端链路没有测试锁定。

**验证方式**：新增 `WorkspaceBindingTests`，驱动**真实 HTTP handler**
（`start_remote_api` + 真 SQLite + 真 conversations/workspaces 表）：
`POST /api/workspaces`（建工作区，路径带空格和中文）→ `POST /api/conversations`
（关联 workspace_id）→ `POST /api/chat/stream`（request_id + conversation_id）
→ Agent run 建成 → 断言 run 的 `conversation_id` 归属正确，且**第一个模型请求的
messages 里真的包含工作区名和绝对路径**。另锁定注记源码不含任何放宽授权的表述
（授权仍归客户端盾牌面板的 roots/确认机制，不自动扩大）。

### P1-9 插话与动态重规划稳定性

| 任务书问题 | 修复 | 证据 |
|---|---|---|
| 同一请求重复发送重复建任务 | 直接端点不带 request_id 时用父 run 推导确定值 `intj_<rid>`；`interjected` 标记 + `interject_child` 记录，同一插话内容的重试**幂等返回原 child** | `test_same_interject_request_retried_returns_the_same_child` |
| 快速连续插话状态竞争 | 同一父任务只重规划一次；不同内容明确报错指引续跑/新消息 | `test_different_interject_on_one_parent_is_refused` |
| 旧任务终态事件覆盖新任务 | 前端事件按 run_id/request_id 双路由（P16 已建），本次回归锁定 | `test_p16_interject` 全组 |
| 插话时旧工具仍在执行 | 迟回执只落 step 不改终态（见 P0-5b） | `test_late_tool_result_never_flips_a_paused_run` |
| 插话失败输入丢失 | 前端 `pendingInterjectOf` 发送前清空，失败时（apiStream 失败 / 抛异常）恢复目标与输入框文本，并 `loadMsgs(true)` 重新同步会话状态 | 代码路径（`pages.js` send() 两处恢复点）；JS 语法校验通过 |
| 断线重连无法确定有效任务 | `/api/agent/runs/active` + 前端 uncertain 态（P16 已建），本次回归锁定 | `test_p16_interject` / agent-state 既有组 |
| **插话后重复执行已完成写操作** | `create(resume_from=…)` 时把父 run **已完成且非只读**的工具步骤的派发键（input_digest）继承进子 run 的 calls 表；模型原样重调时命中复用、回放父 run 回执，不真执行。只搬写操作：读类派发键带 call_id 且跨 run 缓存旧读取会返回过期数据，故意不搬 | `test_interject_child_does_not_replay_the_parent_write`（断言 invoke 零次调用 + tool_reused 事件）；反向验证：回退后写操作真的第二次执行 |

四种操作语义保持区分：cancel→cancelled、pause→paused/paused_by_user、
interject→旧 run paused/interjected + 新 run `replan=True`、新消息→无父 run
（`test_p16_interject.py` 首条测试即断言这点）。

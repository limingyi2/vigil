# 检查点摘要与断点续跑（checkpoint + resume）

日期：2026-10-20 ｜ 分支：`codex/agent-long-task-fix-dev-sync` ｜ 前置：`28aa860` 长任务修复 + `f6bd86e` dev 整合

## 结论

长任务从"能跑通"推进到"具备小时级自治骨架"：上下文可以**封顶**（检查点简报替换历史，不再只靠 `_compact` 缩内容），中断的任务可以**从台账续跑**（不依赖内存传参，进程重启也能续）。单测与真 MiMo 隔离验收均通过。

## 设计

### 检查点摘要（brain/agent_runs.py）

- 触发：每完成 `agent_execution.checkpoint_every` 轮模型请求（默认 30，0 关闭），在下一轮请求前执行一次摘要调用。
- 摘要请求**照常吃预算**（走 `_step` 记账），不带工具清单；失败不致命（fail-open，`checkpoint_failed` 计数，原历史照用）。
- 成功后历史被替换为 `[系统, 任务原文, 简报]` 三条 —— 任务原文锚点在 run 启动时从初始消息的最后一条 user 捕获。
- 简报写进台账（`item.checkpoint` / `item.checkpoint_step`），发 `checkpoint` 事件；同时它就是 resume 的种子。
- 简报格式强制四节：【目标】【已完成】【关键发现】【下一步】（`CHECKPOINT_PROMPT`）。

### 断点续跑（`agent_runs.resume()` + `POST /api/agent/runs/<rid>/resume`）

- 只接受 `STOPPED` 状态的 run；新 run 是**全新预算、全新历史**，`resume_from` 指回父 run，父 run 发 `resumed` 事件。
- **种子由 `_run` 启动时从台账自行推导**：父 run 有检查点简报就用它，没有就 `_steps_digest()` 从步骤本地拼摘要（模型步 content + 工具步结果，各截 500 字符，总 6000）。不经过内存传参 —— create 与执行之间进程重启也能续。
- 原 run 台账不可变；续跑关系只记在新 run 上。

### 与既有机制的关系

- `_compact`：按体积缩内容，不删消息 —— 解决"请求体被拒"；检查点：替换历史 —— 解决"注意力稀释"。两者叠加使用。
- `_clip` 的续读提示在检查点替换后失去意义（原文已归档），简报里已明确告知模型"需要细节请重新调用工具"。

## 边界与后续

- 简报替换会丢弃旧工具结果原文；对"后面还要大量回看早期原始数据"的任务，应靠重新调工具取回（提示词已引导）。
- 检查点摘要本身花一次模型调用（预算内）；MiMo-flash 上约 20~30s。

## 第二批：看门狗 + 预算放开 + 发送键三态（同日追加，提交 cd214a3 之后）

### 看门狗 v1（同参工具停滞检测）

- 信号：`_tool` 返回 `(result, reused)`，`reused` 表示这次调用被签名去重挡下、直接回了缓存结果。
- 连续 `reused` 达到 `WATCHDOG_REUSE_NUDGE`（3）：往上下文注入一条提醒（"重复同样的调用不会得到新信息，换方法或给结论"）；达到 `WATCHDOG_REUSE_STOP`（6）：`_finish(paused, 'stalled')` 停车保护预算，可续跑。
- 预算只管"跑了多久"，看门狗管"有没有在往前走"；参数不同的调用永远不触发。

### 预算上限放开

- `HARD_LIMITS`：max_steps 500→2000，max_requests 200→600，max_tool_calls 300→1000，max_seconds 7200→28800（8 小时）。默认预算不变，配置现在可以往小时级调。

### 用户暂停（paused 状态）

- `POST /api/agent/runs/<rid>/pause` → `_finish(paused, 'paused_by_user')`。`paused` 加入 `STOPPED`：进程重启不会被改写成 interrupted；resume 对它照常可用。

### 发送键三态（client/src/js/pages.js + index.html）

- 发送（↑）→ 运行中变**暂停**（⏸，点击调 pause）→ 停在可续跑状态变**继续**（▶，点击经聊天流续跑）。输入框一旦有字，优先发新消息，按钮自动回到发送。
- 续跑走同一条聊天 SSE：`/api/chat/stream` 新增 `resume_of` 参数，服务端 resume 新 run 时采用客户端 request_id，事件直接投影进会话气泡（含乐观气泡"▶ 继续上次任务"）。
- 会话切换/历史刷新会恢复按钮状态：最近一条 chat 记录若停在 paused/paused_budget/interrupted/failed，发送键恢复成"继续"。
- 🔴 踩过的坑：resume 与新建分支必须互斥（elif）——resume 刚建的 run 用同一个 request_id，新建分支的 find_request 会立刻查到它，拿空 text 再 create 报"request_id 已用于不同请求"，客户端收到 400 但任务其实已在跑。

### 验收

- 单测 +4：pause 语义（含重启不改写、客户端 request_id 透传）、停滞提醒+停车、参数不同不触发、HARD_LIMITS 放开与越界拒绝；全仓 pytest EXIT 0。
- 真 MiMo 隔离（`_tmp/ckpt-audit/drive_pause.py`）：6 秒处 pause → `paused/paused_by_user`；经 `/api/chat/stream` 带 `resume_of` 续跑 → 233 条 SSE 事件、`agent_run` 事件带客户端 request_id、run `succeeded` 且 `resume_from` 指向原 run，答复完整覆盖四步汇总。VERDICT: PASS。
